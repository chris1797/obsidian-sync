# squash 머지는 머지 안 됨으로 보인다

브랜치를 지워도 되나 보려고 `git branch --merged main` 을 돌렸는데, 분명 PR 로 다 들어간 브랜치가 목록에 없었다. 내용은 다 들어갔는데 git 은 "머지 안 됨" 이라고 한다. 둘 다 맞는 말이다 — git 이 묻는 질문과 내가 묻는 질문이 달랐다.

## git 은 족보를 본다

git 의 "머지됐다" 는 **"그 브랜치 끝 커밋이 base 의 조상 사슬 안에 있다"** 는 뜻이다. 내용이 같은지는 보지 않는다. 족보에 이름이 올라 있느냐만 본다.

squash 머지는 브랜치 커밋 A·B·C 를 **새 커밋 S 하나로 다시 써서** base 에 올린다. S 는 A·B·C 와 내용은 합이 같지만 **다른 커밋**이다. 그래서 base 족보에는 S 만 있고 A·B·C 는 없다.

- `git branch --merged` → 브랜치 끝 C 가 base 조상이 아니므로 목록에서 빠진다
- `git log base..branch` → "branch 에서 닿고 base 에서 안 닿는 것" 이니 A·B·C 를 계속 보여준다 — 이미 반영된 것인데도

rebase 머지도 같은 이유로 커밋 해시가 바뀌어 똑같이 보인다. 그래프를 그대로 잇는 건 일반 merge 커밋뿐이다.

## 그래서 내용으로 판정한다

질문을 "커밋이 들어갔나" 에서 **"내용이 base 에 있나"** 로 바꾼다.

```sh
git diff <branch> <base> -- <경로>
```

비어 있으면 그 경로의 내용은 base 와 같다 — 지워도 잃는 게 없다. 단, 브랜치 이후 base 가 그 경로를 또 고쳤으면 차이가 나오니, 그 차이가 누구 쪽 변경인지는 눈으로 가른다.

`--merged` 는 "목록에 있으면 안전" 은 확실하지만, "목록에 없으면 위험" 은 squash 를 쓰는 레포에선 거짓 경보일 수 있다. 판정 도구가 **한쪽 방향으로만 믿을 만하다**는 게 요점.

> 왜 여기 붙나: git 이 커밋 그래프로 판단한다는 축이 가장 크게 어긋나는 지점 — 내용과 족보가 갈라진다

# 툴 정의 필드의 소비자

[[툴 정의가 LLM에 도달하는 경로]]에 `tools/list`가 실어 보내는 건 `name`·`description`·`inputSchema` **셋뿐**이라고 적어뒀다. 틀린 문장은 아닌데 주어가 빠져 있었다. 스펙의 `Tool` 객체 자체는 **일곱 칸**이다.

| 필드 | 필수 | 누가 읽나 |
|---|:---:|---|
| `name` | ✓ | 모델 |
| `inputSchema` | ✓ | 모델 |
| `description` | | 모델 |
| `title` | | 클라이언트 — UI 라벨 |
| `outputSchema` | | 클라이언트 — 응답 검증·파싱 |
| `annotations` | | 클라이언트 — 승인 프롬프트·표시 판단 |
| `_meta` | | 벤더 확장 — 아는 쪽만 |

정확한 문장은 "셋뿐"이 아니라 **"셋만 모델에게 간다"** 였다. 나머지 넷은 버려지는 게 아니라 **다른 독자에게 간다.** 이 구분을 못 하고 있어서 두 번 헛발질했고, 두 번이 서로 반대 방향이라 오히려 기억에 남는다.

## `outputSchema` — 모델에게 옮겨 실을 칸이 아예 없다

"툴이 뭘 돌려주는지 미리 알려주면 모델이 결과를 더 잘 다루지 않을까" 싶어 응답 구조를 `outputSchema`로 선언하려 했다. 안 된다. 클라이언트가 게을러서가 아니라 **구조적으로 못 한다.**

클라이언트가 모델에게 툴을 알려줄 때 쓰는 건 MCP가 아니라 **벤더의 API 형식**이다. 그 형식에 출력 스키마를 적을 칸이 없다.

| 벤더 API의 툴 정의 | 있는 칸 |
|---|---|
| Anthropic Messages API | `name` · `description` · `input_schema` |
| OpenAI function calling | `name` · `description` · `parameters` |

둘 다 **입력 스키마만** 있다. 그러니 클라이언트가 `outputSchema`를 멀쩡히 받아도 모델 컨텍스트로 옮겨 실을 자리가 없다 — 자기 손에 쥐고 응답을 검증·파싱하는 데 쓸 뿐이다. 서버가 아무리 정성껏 채워도 모델은 끝까지 모른다.

여기서 배운 건 MCP 지식이 아니다. **프로토콜이 필드를 정의한다고 해서 그 정보가 최종 소비자에게 도달하는 건 아니다.** MCP는 서버↔클라이언트 사이의 계약일 뿐이고, 그 뒤에 **클라이언트→모델이라는 계약이 하나 더** 있다. 두 계약의 표현력이 다르면 좁은 쪽이 이긴다.

[[MCP 서버 조합 (프록시·집계)]]에서 "중계기는 자기가 아는 것만 옮긴다"고 적었는데, 그건 **같은 층에서** 나는 손실이었다. 이건 층이 바뀌면서 나는 손실이라 더 고약하다 — 중계기는 바꿔 끼울 수 있어도 벤더 API 형식은 내가 못 바꾼다.

## `annotations` — 반대편에서 막혔다

`ToolAnnotations`는 `title`·`readOnlyHint`·`destructiveHint`·`idempotentHint`·`openWorldHint`를 갖는다. 이건 정반대 성격이다. **애초에 모델이 아니라 클라이언트 프로그램이 읽으라고 만든 필드**다 — "이 툴을 부르기 전에 사용자에게 승인을 물을까", "UI에 위험 표시를 붙일까"를 판단하라는 것.

소비자가 처음부터 클라이언트이니 위의 제약에 걸리지 않는다. 모델에게 안 가는 게 정상이라 잃을 게 없다. 그래서 "그럼 이건 채워도 되겠네" 하고 규약으로 세우려다 **다른 벽**에 부딪혔다.

**클라이언트가 그 필드를 실제로 읽는다는 근거가 있어야 한다.** 조사해 보니 Claude Code 공식 문서에는 MCP 표준 annotation(`readOnlyHint` 등)을 어떻게 처리하는지가 **명시돼 있지 않았다.** 대신 벤더 전용 필드(`anthropic/requiresUserInteraction`, `anthropic/maxResultSizeChars`, `anthropic/alwaysLoad`)가 따로 문서화돼 있었다. 표준 필드는 조용하고 확장 필드는 문서가 있는, 좀 얄궂은 그림이다.

동작을 관찰해서 "쓰는 것 같다"까지는 갈 수 있다. 그런데 그건 **계약이 아니라 관찰**이다. 관찰은 다음 릴리스에 말없이 바뀌어도 아무도 잘못한 게 없다. 그래서 규칙 하나가 남았다.

> **문서화되지 않은 동작 위에 규약을 세우지 않는다.** 여러 프로젝트로 퍼질 규약이면 더욱.

[[문서에 남길 것]]에서 "코드에서 파생 가능한 건 파생시키고 계산 안 되는 것만 저장한다"고 갈랐는데, 여기선 축이 하나 더 있다 — **남의 문서에 없는 동작은 애초에 내가 저장할 수 있는 종류의 사실이 아니다.**

## 두 실패가 같은 질문으로 모인다

`outputSchema`는 **소비자가 못 받아서** 죽었고, `annotations`는 **소비자가 읽는다는 보장이 없어서** 죽었다. 둘 다 "내가 잘 채웠는가"와 무관하게 죽었다. 그래서 필드를 볼 때 순서가 바뀌었다.

1. ~~이 필드에 뭘 적어야 잘 적는 건가~~
2. **누가 이걸 읽나. 읽는다는 근거는 어디 있나.**

계층을 여러 개 넘는 필드·메타데이터는 **가장 좁은 관문이 전체 가치를 정한다.** 주는 쪽이 아무리 잘 채워도 받는 쪽이 안 쓰면 값은 0이고, 중간이 아무리 성실해도 마지막 칸이 없으면 0이다. 곱셈이라 어디 한 군데만 0이면 끝이다.

덧붙여 이건 공짜로 실패하지도 않는다. 선언한 `outputSchema`는 [[툴 정의 payload의 비용 분포]]에서 잰 그 `tools/list` 응답에 같이 실린다. **모델에게 도달하지 않으면서 자리는 차지하는** 필드가 된다 — 값이 0이 아니라 음수다. 실제로 그런 게 나도 모르게 붙어 있었는데, 그 경위는 [[능동적인 기본값]]에 따로 적었다.

## 남은 의문

- "누가 실제로 소비하는가"를 **언제** 확인해야 하나. 설계 전에 전부 확인하면 과하고(계층마다 문서를 다 뒤져야 한다), 구현 후에 확인하면 늦다. 이번엔 둘 다 구현 직전에 걸렸는데 운이었던 것 같다
- 관문이 곱셈이라면 **관문 수를 줄이는 게 필드를 잘 채우는 것보다 먼저**인가. 중계 계층을 하나 걷어내는 쪽이 남는 장사일 때가 있을 듯
- `_meta`·벤더 확장 필드는 문서가 있으니 계약은 되는데, 그건 그 벤더에만 묶인다. **표준 필드는 조용하고 확장 필드는 문서가 있을 때** 뭘 고르는 게 맞나

> 상태: #wip — 두 필드의 실패 경위와 그 공통 구조까지. 다음 가지: 관문이 여러 개인 설계에서 확인 시점을 언제로 잡을 것인가.

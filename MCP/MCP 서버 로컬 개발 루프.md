# MCP 서버 로컬 개발 루프

MCP 서버에 툴을 하나 추가할 때 실제로 도는 한 바퀴. [[MCP]] 가 "무엇인가" 라면 이건 "어떻게 만지는가" 다. 웹 서버를 만들 때와 다른 점이 셋 있는데, 전부 **MCP 서버가 브라우저로 열어볼 수 없는 물건**이라는 데서 나온다 — 화면이 없으니 눈으로 확인할 수단을 따로 만들어야 한다.

## 0. 백엔드를 어디로 붙일지 먼저 정한다

내가 만드는 MCP 서버가 [[MCP]] 에서 말한 "외부 서비스를 감싼 껍데기" 라면, 툴을 부르는 순간 **껍데기 뒤의 진짜 API 로 요청이 나간다.** 개발 중이라고 봐주지 않는다. 그래서 붙일 곳을 먼저 정하지 않으면 첫 호출이 그대로 실서버로 간다.

| 백엔드 주소 | 쓰는 때 |
| --- | --- |
| 로컬 목서버 | 응답 모양까지 보고 싶을 때 |
| **도달 불가 주소**(`127.0.0.1:9` 같은 빈 포트) | 툴 등록·인자 전달·실패 처리만 볼 때. 실서버에 트래픽이 안 간다 |
| 실서버 | 진짜 데이터가 필요할 때만. 호출이 로그에 남는다 |

두 번째가 의외로 자주 쓰인다. **연결이 실패한다는 것 자체가 검사 도구**가 된다 — 요청이 조립돼서 나갔다는 뜻이고, 그 실패가 예외로 튀지 않고 정해진 형태로 돌아오는지까지 한 번에 본다.

이때 주소를 환경변수로 주는데, 여기서 [[프로세스 환경은 시작할 때 복사된다]] 가 그대로 걸린다. `.env` 에 적어두기만 하면 서버 프로세스는 그 값을 모른다. 누가 읽어서 넣어주는 경로(실행 스크립트 등)가 있어야 한다.

## 1. 툴을 추가하고 — 서버를 반드시 재시작한다

가장 많이 헤매는 지점. **툴 정의는 프로세스 메모리에 있다.** 데코레이터는 모듈이 import 될 때 한 번 실행되고, 그 결과가 서버 인스턴스에 등록된 채로 남는다. 그러니 파일을 저장해도, 설명 한 줄만 고쳐도 반영되지 않는다. 웹 개발의 핫 리로드 감각으로 접근하면 "왜 안 바뀌지" 로 30분을 쓴다.

같은 이유로, 새 파일에 툴을 만들었으면 그 모듈을 **어딘가에서 import 해야** 등록된다. 파일만 만들어두면 데코레이터가 아예 실행되지 않아서 툴이 없는 것과 같다.

## 2. 등록됐는지는 `tools/list` 로 본다

[[MCP]] 의 6단계 흐름에서 3단계(LLM 주입)에 실려 가는 게 이 목록이다. 그리고 **LLM 에 도달하는 건 `name`·`description`·`inputSchema` 셋뿐이다.** 내가 아무리 잘 쓴 `docs/*.md` 도, 코드 주석도 LLM 은 못 본다. 그래서 툴을 추가한 뒤 확인해야 할 건 "파일이 저장됐나" 가 아니라 "이 셋이 의도대로 나가나" 다.

서버를 안 띄우고도 볼 수 있다. 툴 모듈을 import 한 뒤 `list_tools()` 를 직접 부르면 이름과 필수 인자, 스키마가 그대로 나온다. 파라미터 제약(열거값·범위)을 타입으로 표현했다면 그게 `inputSchema` 에 실려 있는지도 여기서 확인한다 — 실려 있지 않으면 LLM 입장에선 없는 규칙이다.

## 3. 호출은 두 경로가 있고, 보는 것이 다르다

**빠른 쪽 — 파이썬 함수를 직접 부른다.** 툴은 결국 그냥 async 함수라 import 해서 호출하면 된다. MCP 계층을 통째로 건너뛰므로 인자 조립과 응답 가공만 본다. 서버를 띄울 필요도 없어서 반복이 빠르다.

**정확한 쪽 — MCP 프로토콜로 부른다.** 실제 클라이언트가 지나는 길 그대로다. `initialize` 로 세션을 받고, 그 세션 id 를 이후 요청에 실어 `tools/call` 을 보낸다. 직접 호출로는 안 보이던 것들이 여기서 드러난다 — 스키마 검증, 직렬화, 세션 관리, 전송 계층의 문지기.

**둘 다 필요하다.** 직접 호출만 하면 "함수는 되는데 툴로는 안 되는" 상태를 놓치고, 프로토콜 호출만 하면 반복이 느려 개발이 안 된다. 평소엔 직접 호출로 돌리고, 굳히기 전에 프로토콜로 한 번 통과시키는 식.

## 4. stdio 로 확인할 땐 stdout 을 오염시키지 않는다

[[MCP]] 의 "두 개의 통로" 가 여기서 실전 함정이 된다. stdio 전송에서는 **stdout 자체가 프로토콜 채널**이다. 서버가 `print()` 로 진단 메시지를 한 줄만 흘려도 클라이언트는 그걸 JSON-RPC 메시지로 읽으려다 연결을 끊는다. 그래서 진단 출력은 전부 stderr 로 보낸다.

거꾸로 이 성질이 가장 싼 검사가 된다. `initialize` 요청 한 줄을 파이프로 밀어넣어 **stdout 으로 JSON 한 줄이 돌아오면** 서버가 정상적으로 뜬 것이다. 도구도, 클라이언트도 필요 없다.

## 5. HTTP 로 붙을 때 걸리는 것들

- **406 Not Acceptable** — `Accept` 헤더에 `application/json` 과 `text/event-stream` 이 **둘 다** 있어야 한다. Streamable HTTP 가 필요할 때 [[SSE]] 로 전환할 수 있어야 해서 둘 다 요구한다.
- **세션 id** — `initialize` 응답 **헤더**로 내려온다. 본문만 보면 못 찾는다.
- **응답이 SSE 형식** — 본문이 `data: ` 로 시작하는 줄로 온다. 접두사를 떼야 JSON 이다.

## 6. 굳으면 테스트로 잠근다

수동 확인은 방금 만진 툴만 본다. 툴이 늘어나면 **등록 목록 자체를 스냅샷으로 잠그는** 게 실질적으로 가장 값어치가 크다 — 기대 목록과 실제 등록이 다르면 실패하게 해두면, 리팩토링하다 툴을 흘리거나 이름을 잘못 바꾼 걸 바로 잡는다.

여기에 스키마 규약(모든 파라미터가 설명이나 열거값을 갖는지)까지 테스트로 강제해두면, "LLM 이 보는 셋" 의 품질이 사람 리뷰가 아니라 게이트로 유지된다.

## 함정 요약

| 증상 | 원인 |
| --- | --- |
| 설명을 고쳤는데 그대로다 | 서버를 재시작하지 않았다 |
| 새로 만든 툴이 목록에 없다 | 그 모듈을 아무도 import 하지 않는다 |
| 환경변수가 안 먹는다 | 파일에만 있고 프로세스로 옮겨주는 경로가 없다 |
| stdio 로 붙자마자 끊긴다 | 진단 출력이 stdout 으로 나가 프로토콜을 오염시켰다 |
| HTTP 로 406 이 온다 | `Accept` 에 두 타입이 다 없다 |

# MCP 서버 조합 (프록시·집계)

**내 MCP 서버가 남의 MCP 서버를 안에 물고, 하나의 창구처럼 다시 내보내는 패턴.** "MCP에 MCP를 붙인다"가 이상하게 들리지만, [[MCP]]의 구조를 보면 오히려 자연스럽다 — MCP 서버는 "민원 창구"고, 창구 직원이 다른 창구에 전화를 걸어 대신 처리해주는 것뿐이다. 여기서 핵심은 **내 서버가 클라이언트인 동시에 서버**가 된다는 것.

## 왜 자연스러운가 — 창구가 창구를 부른다

[[MCP]] 노트의 "민원 창구" 비유를 그대로 이어보자. 클라이언트가 보기엔 내 서버가 창구 하나다. 그런데 그 창구 뒤 직원이, 요청을 받으면 **자기가 또 다른 창구(구글 광고 MCP, 메타 광고 MCP)에 전화를 걸어** 대신 접수한다. 클라이언트는 뒤에서 전화가 몇 통 오가는지 모른다 — 창구 하나만 상대한 줄 안다.

```
클라이언트(LLM 앱)
   │  ① 나를 하나의 MCP 서버로 봄
   ▼
[내 통합 MCP 서버]  ← 여기가 핵심: 서버이면서 동시에 클라이언트
   │  ② 내부에서 각 매체 MCP의 '클라이언트'로 붙음
   ├──▶ 구글 광고 공식 MCP
   ├──▶ 메타 광고 공식 MCP
   └──▶ 네이버 광고 공식 MCP
```

즉 내 서버 안에 **MCP 클라이언트 모듈이 내장**된다. 매체 서버들에 `initialize` 하고, `tools/list`로 툴 목록을 받아오고, 클라이언트 요청이 오면 `tools/call`을 대신 쏴준다. [[MCP]]에서 본 6단계 흐름이 내 서버 안에서 한 겹 더 반복되는 셈.

## 붙이는 두 가지 결 — 멍청한 프록시 vs 똑똑한 집계

여기서 갈린다. 그냥 통과시키느냐, 가공하느냐.

**① Direct Proxy (그대로 통과).** 매체 서버의 툴을 이름 그대로 클라이언트에 노출하고, 호출이 오면 그대로 전달·반환. 내 서버는 배전반일 뿐이다. 빠르게 붙는 대신, 내가 존재할 이유가 약하다 — 클라이언트가 매체 서버들에 직접 붙어도 똑같다.

**② Smart Aggregator (가공·결합).** 여기가 내 서버의 진짜 값어치다. 매체를 **가로지르는** 로직을 툴로 정의한다.

- "구글 광고 A의 ROI와 네이버 광고 B의 CTR을 비교해 예산 재배치" → 내 서버가 여러 매체 툴을 순서대로 부르고, 결과를 **내 내부 광고 DB와 결합**해 표준 포맷으로 정제한 뒤 한 번에 답한다.
- 클라이언트는 매체가 3개인지 5개인지 몰라도 된다. "통합 리포트"라는 툴 하나만 본다.

결론: **프록시만 할 거면 굳이 내 서버를 둘 이유가 약하다. 매체를 가로지르는 가공(cross-platform)이 있을 때 비로소 이 아키텍처가 정당화된다.**

## 좋은 이유 — 파편화를 매체 서버에 떠넘긴다

각 매체 API의 지옥(OAuth 인증, 레이트 리밋, 수시로 바뀌는 스펙)을 **매체 공식 MCP가 대신 짊어진다.** 내 서버는 그걸 직접 구현하지 않고, 매체 스펙이 바뀌어도 공식 MCP 업데이트만 반영하면 된다. 나는 비즈니스 로직(통합 리포팅·예산 자동배분·내부 DB 결합)에만 집중.

> 단, 전제가 있다: **"매체 공식 MCP가 실제로 존재하고 관리된다"**. 광고 매체들이 공식 MCP를 내놓았는지는 확인이 필요한 부분 — 없으면 결국 내가 [[REST API]]를 직접 감싸는 껍데기 MCP를 만들어야 한다([[MCP]]의 "외부 서비스를 감싼 껍데기" 그대로).

## 대가 — 공짜가 아니다

단정적으로 "매우 좋다"고 하기 전에 비용을 봐야 한다.

- **툴 폭증 → 토큰 폭증.** 매체 5개를 붙이면 각 서버 툴이 전부 클라이언트에 노출된다. 이건 [[FastMCP 대규모 도구의 토큰 절약]]에서 다룬 "도구 500개" 문제 그 자체다. 그대로 다 내보내면 LLM이 매 호출마다 전 매체 툴 스키마를 읽어야 한다. **allowlist·태그로 필요한 것만 노출**하는 게 이 패턴에선 선택이 아니라 필수.
- **이름 충돌 → 네임스페이스 필수.** 구글·메타가 똑같이 `get_campaigns`를 노출하면 클라이언트가 어느 걸 부를지 모른다. 내 서버에서 `google_get_campaigns`, `meta_get_campaigns`처럼 **매체 접두사(namespace)**를 붙여 재노출한다.
- **홉(hop)이 는다 → 지연·장애점 증가.** 클라이언트 → 내 서버 → 매체 서버, 한 단계가 더 낀다. 매체 서버 하나가 죽으면 내 통합 툴이 부분 실패한다 — 부분 실패를 어떻게 응답할지(일부 매체만 성공) 설계가 필요.
- **인증 토큰 파이프라인.** 매체 OAuth 토큰을 내 서버가 환경변수로 쥐고 주입할지, 클라이언트가 호출 때 파라미터로 넘길지 정해야 한다. 내 서버가 여러 매체 자격증명의 **집결지**가 되므로 보안 부담이 한 곳에 쏠린다.

## 한 줄 판단

**매체를 가로지르는 가공(비교·통합·재배치)이 목적이면 좋은 방향.** 단순 중계면 굳이 층을 늘리지 말 것. 붙이는 순간 툴 폭증·네임스페이스·홉 지연이 따라오니, [[FastMCP 대규모 도구의 토큰 절약]]의 allowlist를 처음부터 같이 설계한다.

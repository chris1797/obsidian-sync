# 툴 정의가 LLM에 도달하는 경로

[[MCP]]에서 `tools/list`가 "툴 목록 + 입력 스키마"를 반환한다고만 알고 넘어갔는데, 실제로 서버를 만들다 보니 **그 응답에 뭐가 실리는지가 곧 LLM이 아는 전부**였다. 셋뿐이다.

| 전달 항목 | 어디서 나오나 |
|---|---|
| `name` | 툴 등록 시 준 이름 |
| `description` | 함수 docstring |
| `inputSchema` | 함수 시그니처 + 타입 힌트 |

여기 없는 것은 **LLM에게 존재하지 않는다.** 이게 생각보다 무겁다.

> 나중에 스펙을 열어보니 `Tool` 객체 자체는 일곱 칸이었다. 위 표가 틀린 건 아니고 — **셋만 모델에게 가고** 나머지는 클라이언트가 읽는다. 그 갈림과 거기서 걸린 두 번의 실패는 [[툴 정의 필드의 소비자]]에 따로 적었다.

## 문서 파일은 안 간다

레포에 아무리 잘 쓴 `docs/tools.md`가 있어도 LLM은 그걸 못 연다. MCP 클라이언트가 파일 시스템을 뒤지는 게 아니라, 서버가 보내준 JSON만 보기 때문이다.

그래서 docstring 끝에 `상세: docs/tools.md` 같은 걸 붙여두면 **사람에게만 의미 있는 죽은 포인터**가 된다. LLM은 그 경로를 열 수 없고, 열려고 시도할 수도 없다. 나는 한동안 이걸 "docs가 백업 역할을 한다"고 착각하고 있었는데, 백업이 아니라 **다른 독자를 위한 다른 문서**였다.

정리하면 역할이 갈린다.

- **docstring·스키마** — LLM용. 여기 없으면 LLM이 모른다
- **레포 문서** — 사람용. 여기 있는 게 LLM 동작을 바꾼다고 가정하면 안 된다

## 파라미터 제약은 docstring이 아니라 스키마로

처음엔 습관대로 docstring에 다 적었다.

```python
async def list_campaigns(status: Optional[str] = None, limit: Optional[int] = None):
    """캠페인 목록 조회.
    선택: status(허용: ACTIVE,PAUSED,ARCHIVED), limit(1~100, 기본 25).
    """
```

그런데 타입 힌트에 실으면 **같은 정보가 파라미터별로 붙어서** 간다.

```python
Status = Literal["ACTIVE", "PAUSED", "ARCHIVED"]              # → enum
Limit  = Annotated[Optional[int], Field(ge=1, le=100,
             description="페이지당 건수(1~100, 기본 25)")]      # → minimum/maximum/description

async def list_campaigns(status: Optional[Status] = None, limit: Limit = None):
    """캠페인 목록 조회. ..."""
```

바뀐 점이 셋이다.

1. **위치** — 설명이 툴 전체가 아니라 해당 파라미터에 붙는다. LLM이 그 인자를 채울 때 바로 옆에 있다
2. **검증** — `Literal`은 enum이 되고 범위는 `minimum`/`maximum`이 된다. 문장은 어길 수 있어도 스키마는 못 어긴다
3. **분량** — docstring에서 중복이 빠져 **정보는 늘었는데 설명은 짧아졌다**

세 번째가 반직관적이라 기억에 남는다. "설명을 늘리면 길어진다"가 아니라, **적을 자리를 옮기면 둘 다 좋아지는** 경우가 있다.

## 중계 계층이 있으면 더 좁아진다

내 서버 앞에 상위 게이트웨이가 끼어 그걸 통해 LLM이 접근하는 구조였는데, 그 게이트웨이가 `tools/list`와 `tools/call`만 프록시하고 있었다. 그러면 서버가 아무리 리소스나 프롬프트를 노출해도 **중계되지 않아 도달하지 않는다.** 서버 자신의 `instructions`도 마찬가지다 — 게이트웨이가 자기 이름으로 새 서버를 세우기 때문.

교훈: **"내 서버가 무엇을 노출하는가"와 "클라이언트가 무엇을 받는가"는 다른 질문이다.** 중간에 뭐가 끼어 있으면 반드시 실제 전달분을 확인해야 한다. [[MCP 서버 조합 (프록시·집계)]]에서 서버가 클라이언트를 겸하는 구조를 봤는데, 그 구조의 대가가 여기서 나온다 — 중계기는 자기가 아는 것만 옮긴다.

## 그래서 얼마나 아껴야 하나

여기까지 오면 "그럼 description을 최대한 줄여야겠네"로 가기 쉬운데, 실제로 재보면 그렇지 않다. [[툴 정의 payload의 비용 분포]]에 따로 적었다. [[FastMCP 대규모 도구의 토큰 절약]]의 절약 전략도 이 구분 위에서 읽어야 한다 — 줄일 수 있는 것과 줄여도 티가 안 나는 것이 갈린다.

## 남은 의문

- 툴이 아닌 노출 방식(`resources`·`prompts`)은 클라이언트가 지원해도 **사람이 명시적으로 골라야** 쓰이는 것 같은데, 그렇다면 "LLM이 자율적으로 참조하는 배경지식"을 서버가 밀어넣을 방법은 사실상 없는 건가?
- 그 경우 배경지식도 결국 툴 하나로 감싸는 게 유일한 길인가

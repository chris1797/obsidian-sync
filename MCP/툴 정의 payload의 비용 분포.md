# 툴 정의 payload의 비용 분포

[[툴 정의가 LLM에 도달하는 경로]]를 알고 나면 자연스럽게 다음 질문이 온다 — **그 셋 중 뭐가 제일 비싼가.** 툴 목록은 매 요청마다 컨텍스트에 실리니까 여기서 아끼면 계속 아낀다.

나는 당연히 `description`이라고 생각했다. 사람이 쓴 산문이고, 길어지기 쉽고, [[FastMCP 대규모 도구의 토큰 절약]]류의 조언도 늘 "도구 설명을 줄여라"라고 하니까. 그래서 툴 설명을 늘릴 때마다 찜찜했다.

재보니 틀렸다.

## 실측

읽기 전용 툴 27개(파라미터 235개)짜리 서버의 `tools/list` 응답 전체를 글자 수로 쪼갠 결과다.

| 구간 | 글자 | 비중 |
|---|---:|---:|
| `name` | 584 | 1.4% |
| `description` (툴 설명) | 6,251 | 15.5% |
| `inputSchema` | 33,604 | **83.1%** |
| ├ 파라미터 `description` | 7,193 | 17.8% |
| ├ 자동 생성 `title` | 4,684 | 11.6% |
| └ JSON 골격 (`type`/`anyOf`/`default`) | 21,727 | **53.7%** |

**사람이 쓴 글자는 33%뿐이고, 나머지 65%는 기계가 만든 구조다.** 툴 설명만 보면 15%다.

## 왜 골격이 그렇게 무거운가

선택 파라미터 하나가 이런 모양으로 펼쳐진다.

```json
"after": {
  "anyOf": [{"type": "string"}, {"type": "null"}],
  "default": null,
  "title": "After",
  "description": "다음 페이지 커서…"
}
```

`Optional[str]` 한 줄이 `anyOf` 배열 + `null` 분기로 부풀고, 여기에 필드명을 그냥 띄어쓰기로 바꾼 `title`("After")이 자동으로 붙는다. **정보량이 0인데 글자는 먹는다.** 파라미터가 235개면 이게 235번 반복된다.

## 그래서 뒤집히는 판단

- **툴 설명을 늘리는 건 생각보다 싸다.** 설명을 두 배로 늘려도 전체는 15% 증가한다. "짧게 쓰느라 정확도를 깎는" 거래가 손해인 구간이 넓다
- **파라미터 설명을 스키마로 옮기는 건 거의 공짜다.** 어차피 그 파라미터의 JSON 골격은 이미 실려 있고, 거기 `description` 한 줄이 더 붙을 뿐이다
- **정말 줄이려면 파라미터 수를 줄여야 한다.** 설명 문장이 아니라 골격이 문제니까, 안 쓰는 선택 파라미터 하나를 빼는 게 문장 다듬기보다 효과가 크다
- `title` 억제 같은 건 11%짜리 미시 최적화다. 클라이언트가 UI 라벨로 쓸 수도 있어 손대기 전에 확인이 필요하다

## 남는 교훈

이건 MCP 얘기라기보다 **최적화의 순서** 얘기다. 비싼 곳을 짐작으로 정하면, 눈에 잘 띄는 것(사람이 쓴 산문)을 범인으로 몰고 실제 범인(반복되는 기계 구조)은 그대로 둔다. 재는 데 5분 걸렸고, 그 5분이 "설명을 줄여야 한다"는 몇 주치 찜찜함을 없앴다.

## 남은 의문

- 글자 수 비율이 토큰 수 비율과 얼마나 다를까. JSON 골격은 반복이 심해 토크나이저가 잘 압축할 것 같은데, 그렇다면 골격의 실제 비중은 53%보다 **낮을** 수 있다. 그래도 결론(설명이 주범이 아니다)이 뒤집힐 정도는 아닐 듯
- 파라미터가 많은 툴 몇 개를 쪼개는 것과 그대로 두는 것 중 어느 쪽이 LLM 선택 정확도에 유리한가

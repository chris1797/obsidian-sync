# HTTP 헤더 오버헤드

[[REST API]]의 무상태(stateless)에는 **매 요청이 자기 완결적이어야 한다**는 조건이 붙는다. 서버가 아무것도 기억하지 않으니, 필요한 맥락을 요청마다 다시 실어 보낸다. 그 노트에선 이걸 수평 확장의 대가로만 적었는데, **청구서가 실제로 얼마인지**를 숫자로 본 게 이 노트다.

## 청구서

이벤트 1건(본문 117바이트)을 [[Long Polling]]으로 받을 때 회선을 지나간 것:

```
→ GET /events?since=41 HTTP/1.1
  Host / User-Agent / Accept / Accept-Encoding / Cookie ...   ≈ 600 B
← HTTP/1.1 200 OK
  Content-Type / Content-Length / Date / Server ...           ≈ 170 B
  {"cursor":42,"events":[...]}                                  117 B
                                                     합계   ≈ 885 B
```

**본문 117바이트를 나르려고 봉투에 770바이트.** 87%가 봉투다. 그리고 이 봉투는 매 요청 **거의 글자 하나 안 바뀐 채로** 다시 간다. `User-Agent`는 브라우저를 껐다 켜기 전엔 안 변하고, `Cookie`도 그대로다.

이걸 1,000번 반복하면 884,698바이트. 같은 이벤트를 [[WebSocket]]으로 보내면 119,692바이트니 **7.4배**다. 처음엔 이 숫자를 "long polling이 나쁜 방식이라는 증거"로 읽었는데, 그건 오독이었다.

## 오독을 깬 숫자 — HTTP/2에서 1.5배

같은 long polling을 HTTP/2로 옮기면 182,475바이트가 된다. **코드는 한 줄도 안 바뀌었다.** 방식이 아니라 **전송 계층이 반복을 다루는 방법**이 달랐던 것이다.

범인은 HTTP/1.1이 헤더를 **매번 평문 원문으로** 보낸다는 성질이다. 본문은 gzip으로 압축하면서 헤더는 압축 대상이 아니었다. 짧은 응답을 자주 주고받는 API에서는 압축 안 되는 쪽이 트래픽의 대부분을 차지하게 된다.

## HPACK — 두 번째부터는 번호로 부른다

HTTP/2의 헤더 압축 방식. 원리는 **양쪽이 같은 표를 들고 번호로 지칭**하는 것이다.

```
1번째 요청:  user-agent: Mozilla/5.0 (Macintosh; ...)   ← 원문 전송, 동시에 양쪽 표의 62번에 등록
2번째 요청:  [62]                                        ← 1바이트
3번째 요청:  [62]
```

전화 걸 때마다 이름·주소·생년월일을 다 부르다가, "저 62번 회원이요" 한마디로 끝내는 것과 같다. 그래서 885바이트가 65바이트로 줄어든다.

핵심은 **표를 양쪽이 공유하며 커넥션 내내 유지**한다는 점이다. 그러니까 HPACK이 이득을 보려면 **같은 커넥션에서 요청이 반복돼야** 한다. 요청 하나 보내고 커넥션을 닫아버리면 표가 매번 초기화되니 이득이 없다. HTTP/2의 헤더 압축과 커넥션 재사용은 별개 기능처럼 보이지만 사실 한 몸이다.

여기서 [[백링크]]의 "저장 vs 계산"과 비슷한 감각을 느꼈다. 반복되는 정보를 **매번 실어 나를 것인가, 양쪽이 기억하고 참조만 할 것인가.** 다만 방향은 반대다 — 백링크는 저장 대신 계산을 택했고, HPACK은 전송 대신 저장(양쪽 상태 테이블)을 택했다. **비싼 쪽이 무엇이냐**가 선택을 뒤집는다.

## 무상태의 값이 달라졌다

이 숫자를 보고 나서 [[REST API]] 노트의 무상태 항목을 다시 읽게 됐다. 무상태의 대가는 "요청마다 맥락을 다시 보내는 비용"인데, **HTTP/2가 그 대가를 10분의 1로 깎았다.** 원칙은 그대로인데 가격표가 바뀌었으니 결론도 바뀐다 — HTTP/1.1 시절이라면 접었을 [[Long Polling]]이 HTTP/2에서는 살아남는다.

같은 전환이 [[SSE]]의 오리진당 커넥션 한도도 6개에서 ~100개로 푼다. **인프라 결정 하나가 서로 무관해 보이던 두 제약을 동시에 걷어낸다** — [[실시간 전송 방식 선택]]에서 HTTP/2를 사실상 전제로 깐 이유다.

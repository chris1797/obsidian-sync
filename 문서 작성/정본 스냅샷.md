# 정본 스냅샷

정본이 **내 레포 밖**에 있는 경우가 있다. 외부 워크플로 도구에 정의가 살아 있고 내 코드는 그걸 옮겨온 사본이라든지, 남의 API 명세를 보고 클라이언트를 짰다든지. 이때 정본이 바뀌면 내 코드는 조용히 낡는다. **아무도 알려주지 않는다.**

해법은 싱겁다. **원문을 레포에 그대로 커밋해 둔다.** 그러면 이후 드리프트 확인이 `git diff` 한 번이 된다.

## 없을 때 어떤 일이 벌어지나

비교 기준이 없으면 사람이 정본을 열어 코드와 눈으로 대조해야 한다. 그리고 놓친다.

실제로 하루치 변경 7건을 찾은 적이 있는데, 정본 설명문에 작성자가 `[2026-08-04]` 같은 **날짜 표시를 손으로 남겨둔 덕분**이었다. 그게 없었으면 못 찾았다. 남의 습관에 내 정합성이 얹혀 있던 셈이다.

스냅샷을 넣고 나니 이후엔 스크립트 한 번 + `git diff` 로 끝났다. 그리고 커밋한 바로 그날 정본이 두 번 더 바뀌었는데 **둘 다 자동으로 잡혔다.** 하나는 파라미터 2개 추가, 하나는 항목 2개 신설이었다.

## [[문서에 남길 것]]과 부딪히지 않나

부딪히는 것처럼 보인다. 거기서는 **코드에서 파생 가능한 건 저장하지 말고 계산하라**고 했다. 양쪽에 저장하면 갈라지고, 갈라진 문서는 없느니만 못하다고. 그런데 스냅샷은 정본을 대놓고 복사해 저장하는 짓이다.

구분점은 **역할**이다.

- 문서가 코드를 베끼면 → 그 문서는 **진실을 주장한다.** 그래서 어긋나는 순간 거짓말이 된다
- 스냅샷은 진실을 주장하지 않는다 → **"내가 마지막으로 확인한 시점"의 기록**이다. `diff`의 좌변일 뿐

좌변은 낡아도 괜찮다. 오히려 **낡아야 차이가 보인다.** 스냅샷이 정본과 같아지면 할 일이 없다는 뜻이고, 달라지면 그 차이가 곧 알림이다. 문서 중복은 어긋남이 **버그**지만, 스냅샷은 어긋남이 **기능**이다.

같은 이유로 원리도 뒤집히지 않는다. [[백링크]]에서 역방향을 저장하지 않는 건 "계산할 수 있으니까"인데, **외부 정본은 내 레포에서 계산할 수 없다.** 매번 네트워크로 조회해야 하고, 조회 결과는 시점마다 다르다. 계산 불가능한 것을 저장하는 건 원리 위반이 아니라 원리의 적용이다.

## 지킬 것

- **자동 생성물로 취급한다.** 손으로 고치면 기준점이 오염돼 다음 diff가 거짓말을 한다. 파일 머리에 "직접 편집하지 말 것"을 박아두는 게 좋다
- **멱등하게 쓴다.** 내용이 같으면 파일을 건드리지 않아야 `git diff` 가 신호로 남는다. 매번 타임스탬프 같은 게 바뀌면 diff 가 노이즈로 덮인다
- **가져올 것과 쓸 것을 구분한다.** 스냅샷은 원문 그대로 두고, 그중 내 시스템에 맞는 부분만 골라 코드에 반영한다. 원문에는 내 쪽에서 틀린 서술이 섞여 있을 수 있다(응답 형식이 다르다든지)
- 검사 모드(`--check` 류)를 같이 만들어 두면 CI 에 얹어 자동화할 수 있다

## 어디에 쓰나

정본이 밖에 있고, 그게 조용히 바뀌는 모든 경우.

- 외부 도구/워크플로에 정의된 것을 코드로 옮겨온 경우
- 서드파티 API 명세를 보고 짠 클라이언트
- 팀 밖에서 관리되는 공유 스키마·설정

## 남은 의문

- 스냅샷을 언제 갱신하느냐가 곧 "언제 알아채느냐"다. CI 에 넣으면 매 빌드지만, 정본이 하루에도 여러 번 바뀌면 그것도 노이즈다. 적정 주기는 정본의 변경 빈도에 달린 것 같은데 기준을 못 잡았다
- 정본이 바뀌었을 때 **자동으로 코드까지 고치는** 데까지 가야 하나, 아니면 사람이 판단할 지점으로 남겨야 하나. 지금은 후자가 맞다고 보는데, 반복되는 종류의 변경은 자동화 여지가 있어 보인다

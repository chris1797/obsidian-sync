# heartbeat 와 유휴 커넥션

**침묵은 죽음으로 오해받는다.** 장기 연결([[SSE]]·[[WebSocket]])을 처음 붙였을 때 제일 당황스러운 증상이 이것이다 — 코드는 멀쩡하고 에러 로그도 없는데, 트래픽이 뜸한 새벽에만 연결이 끊긴다.

원인은 앱이 아니라 **중간에 낀 장비들**이다. 그리고 이건 버그가 아니라 그 장비들의 정상 동작이다.

## 왜 끊기나 — 아무도 커넥션을 영원히 기억해주지 않는다

경로에 있는 장비마다 각자의 이유로 유휴 커넥션을 정리한다.

| 장비 | 끊는 이유 |
|---|---|
| 로드밸런서 · 리버스 프록시 | idle timeout(보통 60초). 좀비 커넥션이 슬롯을 먹는 걸 막으려고 |
| NAT 게이트웨이 | 매핑 테이블 항목 만료 |
| 방화벽 | 세션 테이블 만료 |
| 모바일 캐리어 NAT | 배터리·자원 절약을 위해 더 짧게(30초대) |

NAT 쪽이 특히 이해가 늦었다. [[네트워크 경계 (ingress·egress·NAT)]]에서 SNAT가 "출발지 주소를 바꿔치기"한다고 정리했는데, 바꿔치기를 하려면 **"이 내부 주소 ↔ 저 외부 포트"라는 대응표를 들고 있어야 한다.** 그 표는 무한하지 않으니 조용한 항목부터 지운다. 항목이 지워지면 돌아올 패킷이 갈 곳을 잃는다. 그러니까 **연결이 끊긴 게 아니라, 연결을 기억하던 메모가 지워진 것**이다.

여기서 진짜 고약한 점: **양쪽 다 자기가 연결돼 있다고 믿는다.** TCP는 조용히 있는 것과 죽은 것을 구별 못 하므로, 서버는 계속 쓰고 클라이언트는 계속 기다린다. 끊겼다는 사실은 다음 이벤트가 발생하는 순간에야 드러나고, 그 이벤트는 그대로 유실된다.

## 방법 — 조용할 때 의미 없는 것을 보낸다

주기는 **경로에서 가장 짧은 타임아웃보다 짧게.** 15초가 관례인데 근거가 있다 — 흔한 60초 타임아웃 아래에서 한 번 유실돼도 두 번째 기회가 남는다.

[[SSE]]는 주석 줄을 쓴다. 데이터가 아니므로 클라이언트 코드가 볼 일이 없다.

```js
const hb = setInterval(() => res.write(': ping\n\n'), 15_000);
req.on('close', () => clearInterval(hb));   // ← 이거 빠뜨리면 죽은 커넥션에 계속 쓴다
```

[[WebSocket]]은 규격에 ping/pong opcode가 있어서 **응답을 받는다.** 이 차이가 결정적이다.

```js
setInterval(() => {
  for (const ws of wss.clients) {
    if (!ws.isAlive) { ws.terminate(); continue; }  // 지난번 ping 에 답이 없었다 → 사망 판정
    ws.isAlive = false;
    ws.ping();
  }
}, 15_000);
```

`isAlive`를 먼저 `false`로 내리고 ping을 쏘는 순서가 요점이다. 다음 주기에 `pong`이 와서 `true`로 되돌려놨는지를 보고 판정한다. **직전 라운드의 결과로 이번 라운드에 판정**하는, [[컨트롤 루프]]의 "현재 상태와 목표 상태를 반복 대조"와 똑같은 모양이다.

## 두 방식의 비대칭 — 감지냐 유지냐

같은 heartbeat인데 하는 일이 다르다.

- **SSE의 주석** — *유지*만 한다. 단방향이라 응답이 없으니, 상대가 죽었는지 서버는 끝내 모른다. 죽은 커넥션이 리소스를 물고 남는다.
- **WebSocket의 ping/pong** — *유지 + 감지*. 양방향이라 응답이 오는지로 생사를 판정하고 정리까지 할 수 있다.

[[실시간 전송 방식 선택]]에서 SSE를 기본값으로 밀면서도 이 항목만은 WebSocket이 명확히 낫다. SSE로 죽은 커넥션을 회수하려면 애플리케이션 레벨에서 별도 신호를 왕복시켜야 하는데, 그러면 단방향이라는 전제를 스스로 깨는 셈이 된다.

[[Long Polling]]만 이 문제에서 자유롭다. 25초마다 응답이 오가니 유휴 상태가 아예 안 생긴다 — 낭비가 곧 방어인 구조다.

## TCP keepalive 와 헷갈리지 말 것

OS에도 `SO_KEEPALIVE`가 있는데 실무에선 거의 쓸모가 없다. 기본 유휴 시간이 **2시간**이라 60초 타임아웃을 이길 수 없고, 조정하려면 커널 파라미터를 건드려야 하는데 컨테이너 환경에선 그 자체가 일이다. **애플리케이션 레벨 heartbeat가 표준 답인 이유**가 이것이다.

> 상태: #wip — 다음 가지: heartbeat 주기와 모바일 배터리 소모의 트레이드오프, 프록시 idle timeout 을 앱이 알아내는 방법(대개 못 알아내서 보수적으로 잡는다), 죽은 SSE 커넥션 회수 패턴.

> 왜 여기 붙나: 장기 연결의 침묵은 죽음으로 오해받아 중간 장비가 끊는다

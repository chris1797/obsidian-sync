# SSE

**Server-Sent Events.** 끝나지 않는 HTTP 응답 하나로 서버가 클라이언트에게 계속 말하는 방식. [[MCP]] 노트의 각주에서 "서버→클라 단방향 푸시 기술(라디오 방송)"이라고만 적고 넘어갔던 그 SSE를, 여기서 제대로 편다.

라디오 비유를 조금 더 밀어보면 정확해진다. 전화를 걸었는데 상대가 **끊지 않고** 계속 말하고, 나는 들을 수만 있다. 새 기술을 쓴 게 아니라 **평범한 `GET` 응답을 안 닫는 것**이 전부다 — [[Long Polling]]이 "응답을 늦게 보낸다"면 SSE는 "응답을 영원히 안 끝낸다".

## 서버 — 응답을 닫지 않는다

```js
res.writeHead(200, {
  'Content-Type': 'text/event-stream',   // ① 이 값이 EventSource 를 작동시킨다
  'Cache-Control': 'no-store',           // ② 중간 캐시가 스트림을 삼키지 않게
  'X-Accel-Buffering': 'no',             // ③ Nginx 야, 버퍼링하지 마라
  'Connection': 'keep-alive',
});
res.flushHeaders();            // ④ 헤더를 즉시 밀어냄
res.write('retry: 2000\n\n');  // ⑤ "끊기면 2초 뒤 다시 붙어" 를 브라우저에 지시

function send(event, id, data) {
  res.write(`id: ${id}\nevent: ${event}\ndata: ${JSON.stringify(data)}\n\n`);
}
```

③④가 **로컬에선 멀쩡한데 배포하면 침묵하는** 대표 원인이다. 프록시가 응답을 모아뒀다가 한꺼번에 보내려 하면 스트림의 실시간성이 통째로 사라진다. Nginx 쪽에도 `proxy_buffering off;`를 같이 넣어야 한다. 여기서도 [[Long Polling]]과 같은 구도가 반복된다 — **앱 코드는 옳은데 앞단 인프라가 배신한다.**

## 와이어 포맷 — 텍스트 몇 줄이 프로토콜의 전부

소켓에 실제로 나가는 바이트가 사람이 읽을 수 있는 텍스트다. 이게 SSE의 성격을 다 설명한다.

```
id: 42\n
event: trade\n
data: {"sym":"AAPL","px":214.5}\n
\n                    ← 빈 줄이 "이벤트 끝" 신호. 이거 빠뜨리면 영원히 안 온다
```

필드는 넷뿐이다.

| 필드 | 역할 |
|---|---|
| `data:` | 본문. 여러 줄이면 `\n`으로 이어붙여진다 |
| `event:` | 이벤트 이름. 생략하면 `message` |
| `id:` | 브라우저가 기억했다가 재접속 때 되돌려보낸다 |
| `retry:` | 재접속 대기 시간(ms) |
| `: 주석` | 데이터가 아니다 → [[heartbeat 와 유휴 커넥션]] |

프레이밍 오버헤드는 이벤트당 14.2바이트(`id:`까지 붙이면 +11). 117바이트 본문이 131바이트가 되니 [[WebSocket]]의 2바이트보다 7배 비싸지만, **전체로는 10% 차이**다. 텍스트 프로토콜의 대가가 이 정도면 싸다고 봤다.

대가가 진짜 나타나는 곳은 따로 있다 — **텍스트만 보낼 수 있다.** 바이너리를 실으려면 base64로 감싸야 하고 그 순간 33%가 붙는다. 이미지·오디오를 흘려야 하면 SSE는 후보에서 빠진다.

## 클라이언트 — 두 줄

```js
const es = new EventSource('/events', { withCredentials: true });
es.addEventListener('trade', (e) => render(JSON.parse(e.data)));
```

`withCredentials`가 붙은 이유가 중요하다. **`EventSource`는 커스텀 헤더를 못 붙인다.** `Authorization: Bearer ...`를 쓸 방법이 없어서 인증은 쿠키에 기대거나 URL에 단발성 티켓을 실어야 한다. 그런데 쿠키를 쓰는 순간 [[CORS]]의 그 제약이 따라온다 — 자격증명을 보내는 요청에 서버는 `Access-Control-Allow-Origin: *`으로 답할 수 없다. 출처를 정확히 명시해야 한다. 브라우저 API가 헤더를 막아서 쿠키로 밀려나고, 쿠키 때문에 CORS 제약이 따라붙는 이 연쇄가 SSE 붙일 때 제일 자주 걸리는 자리다.

## 이게 기본값인 이유 — 끊김 복구가 공짜

바이트에서 10% 지고도 [[실시간 전송 방식 선택]]에서 SSE가 기본값이 되는 근거는 여기 하나다.

```
1. 연결 끊김 감지
2. retry(2000ms) 대기
3. GET /events 재요청 — 이때 헤더 자동 추가:
      Last-Event-ID: 42        ← 마지막으로 본 id: 값
4. 서버는 이 헤더를 읽어 43번부터 다시 쏜다
```

**1~3을 브라우저가 한다.** 서버가 할 일은 세 줄이다.

```js
const last = Number(req.headers['last-event-id'] || 0);
for (const e of store.since(last)) send(e.type, e.id, e.data);
```

[[WebSocket]]에서 이걸 직접 짜면 [[지수 백오프와 지터]]까지 포함해 20줄이 넘는다. **표준이 대신 해주는 일을 코드로 다시 짜지 않는 것** — 이게 10% 바이트보다 크다고 판단한 근거다.

## 밟은 지뢰 — 오리진당 커넥션 한도

HTTP/1.1에서 브라우저는 **한 출처당 커넥션을 6개**로 제한한다. SSE는 그중 하나를 영구히 점유하므로, 탭을 6개 열면 7번째 탭은 연결조차 못 하고 나머지 API 호출도 굶는다. 원인이 앱 코드 어디에도 없어서 찾기 어려운 종류의 버그다.

HTTP/2로 가면 멀티플렉싱 덕에 ~100개로 풀린다. 그래서 **SSE를 쓰기로 했다면 HTTP/2가 사실상 전제 조건**이다. 같은 HTTP/2 전환이 [[Long Polling]]의 7.4배 낭비도 1.5배로 줄인다 → [[HTTP 헤더 오버헤드]]. 한 인프라 결정이 두 방식의 실용성을 동시에 바꾼다는 게 흥미로운 지점이다.

> 상태: #wip — [[MCP]] 각주에서 갈라져 나온 노트. 다음 가지: 서버 인스턴스가 여럿일 때 어느 인스턴스가 그 커넥션을 물고 있나(sticky vs 백플레인), `Last-Event-ID` 를 신뢰할 수 있는 범위(서버가 이벤트를 얼마나 보관해야 하나).

> 왜 여기 붙나: 끝나지 않는 HTTP 응답 하나로 서버가 계속 말하는 방식

# 실시간 전송 방식 선택

서버에 생긴 일을 클라이언트가 **새로고침 없이** 받는 방법은 셋이다 — [[Long Polling]] · [[SSE]] · [[WebSocket]]. 셋 다 결국 TCP 위에 얹히고, 갈리는 지점은 하나다: **HTTP를 얼마나 오래 붙잡고 있느냐.**

비유가 제일 빠르다. 친구한테 소식 받는 세 가지 방법이다.

- **Long Polling** — 편지를 쓴다. "새 소식 있어?" 친구는 소식이 생길 때까지 답장을 안 보내고 들고 있다가, 생기면 답장한다. 받자마자 **또 편지를 쓴다.** 봉투를 매번 새로 쓴다.
- **SSE** — 전화를 걸어놓고 안 끊는다. 친구가 일방적으로 계속 말한다. 나는 듣기만 한다.
- **WebSocket** — 전화를 걸어놓고 안 끊는다. **둘 다** 말할 수 있다.

## 처음 세운 기준은 틀렸다 — 바이트가 아니다

"뭘 쓰지"를 정하려고 실측 비교를 읽었는데, 정작 **비교표를 보고 나서 판단 기준을 바꾸게 됐다.** 순서대로 적는 게 이 노트의 요점이다.

이벤트 1,000건(각 ~117바이트)을 보냈을 때 실제 회선을 지나간 바이트:

| 방식 | 총 바이트 | WebSocket 대비 |
|---|---|---|
| WebSocket (HTTP/1.1) | 119,692 | 1.0배 |
| SSE (HTTP/1.1) | 131,596 | 1.1배 |
| Long Polling (HTTP/1.1) | 884,698 | **7.4배** |
| Long Polling (HTTP/2) | 182,475 | 1.5배 |

7.4배를 보고 "long polling은 끝났다"고 결론 내리려던 참이었다. 그런데 같은 방식이 HTTP/2에서 1.5배로 내려앉는다. **차이를 만든 게 전송 방식이 아니라 반복되는 HTTP 헤더**였다는 뜻이다 — 이유는 [[HTTP 헤더 오버헤드]]로 따로 뺐다. 여기서 첫 번째 교훈: 수치가 크게 벌어지면 방식을 의심하기 전에 **뭐가 반복되고 있는지**를 본다.

## 예상이 깨진 두 지점

**하나 — 지연시간은 셋 다 같다.** 50ms 네트워크에서 26~27ms로 사실상 동일했다. long polling도 "다음 요청을 쏘기 전에 이벤트가 이미 대기 중"이면 손해가 없다. 무너지는 건 **이벤트 발생 주기가 왕복시간(RTT)보다 짧아질 때**뿐이다. 초당 1건 미만이면 여전히 쓸 만하다는 결론이 여기서 나온다.

**둘 — 메모리는 WebSocket이 제일 싸다.** 유휴 커넥션 500개 기준 WebSocket 13KB · Long Polling 21KB · SSE 23KB. HTTP 응답 객체를 들고 있어야 하는 쪽이 더 비싸다. 다만 이 크기 차이는 커넥션 수가 만 단위로 가기 전엔 결정 요인이 못 된다.

## 진짜 기준 — 무엇을 직접 짜야 하는가

바이트도 지연도 갈라주지 못했으니 남은 축은 **구현 부담**이다. 이 표가 실제 결론이다.

| | Long Polling | SSE | WebSocket |
|---|---|---|---|
| 재연결 | 루프가 곧 재연결 | 브라우저 자동 | **직접 구현** |
| 놓친 이벤트 재개 | `cursor` 쿼리 | `Last-Event-ID` 자동 | **직접 구현** |
| 살아있음 확인 | 불필요 | 주석 한 줄 | ping/pong 프레임 |
| 방향 | 단방향 | 단방향 | **양방향** |
| 바이너리 | ✗ | ✗ | **✓** |
| 이벤트당 오버헤드 | 770B(H1) / 65B(H2) | 14.2B | 2B |

WebSocket을 고르면 [[지수 백오프와 지터]]와 재개 커서를 손으로 짜야 한다. SSE는 그걸 브라우저가 해준다. **2바이트 대 14.2바이트를 아끼려고 WebSocket을 고르면, 그 차액을 코드로 갚는다.**

## 판단 한 줄

> **클라이언트가 서버로 보낼 말이 있는가?** 있으면 [[WebSocket]], 없으면 [[SSE]].

[[Long Polling]]은 "레거시라 어쩔 수 없을 때"가 아니라 **이벤트가 드물고 HTTP/2를 쓸 때** 여전히 합리적인 선택지로 남는다. 이건 [[REST API]]의 무상태 원칙을 깨지 않는다는 장점도 같이 온다 — 나머지 둘은 서버가 커넥션을 물고 있어야 해서 어느 인스턴스나 처리 가능하다는 성질을 잃는다. [[MCP]]가 상시 SSE 채널(stateful)에서 Streamable HTTP(stateless)로 옮겨간 동기가 정확히 이것이다.

셋 중 무엇을 골라도 공통으로 밟는 지뢰가 하나 있는데, 유휴 커넥션이 조용히 죽는 문제다 → [[heartbeat 와 유휴 커넥션]].

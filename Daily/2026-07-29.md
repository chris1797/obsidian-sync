## 만진 것

- 개인 하네스 레포 pull. Obsidian 캡처 규칙과 `obsidian-note` 스킬이 새로 들어와서, 이제 다른 프로젝트에서 개념을 하나 이해할 때마다 에이전트가 "볼트에 남길까요?"를 먼저 물어본다. 자동 기록은 아니고 제안형.
- 이 볼트에 일일 노트 축을 새로 깔았다. `Daily/` 폴더 + 3줄 템플릿. 홈(`개발 세컨드 브레인`)에는 **안 붙이기로** 결정.
- `/doctor` 로 하네스 정리. 271세션 동안 한 번도 안 불린 스킬 11개·플러그인 5개를 껐다. 카파시 가이드 플러그인도 그중 하나였는데, 같은 내용이 이미 `coding.md` 로 상시 로드되고 있어서 중복 사본이었다.
- Obsidian 캡처 규칙을 일일 노트용으로 재작성. 세션 끝에 후보만 던지고 기록은 내가 한다. 사내 정보는 익명화가 아니라 아예 후보에서 뺀다.
- kubectl 설치 진행해봄
- Codex 플러그인 전체 비활성. 게이트는 원래 꺼져 있었고(워크스페이스 10곳 전부 미설정), 실제로는 훅이 매 턴 띄우던 broker 쪽 문제였다. 30시간 떠 있던 좀비 broker 2개도 정리.

## 배운 것

**[[백링크]]가 있으면 링크를 한쪽으로만 걸어도 된다.** 오늘 제일 크게 남은 것.

클로드코드 /doctor 한번씩 해주는거 좋은 듯. 안쓰는 스킬, 플러그인이나 중복되는 것들도 찾아준다.

일일 노트를 홈에 붙일지 고민한 게 결국 이 문제였다. "개념 노트에서 '이거 언제 만졌더라'를 보려면 개념 → 일일로도 링크를 걸어야 하나?" 싶었는데, 안 걸어도 된다. A → B 화살표 하나면 B를 열었을 때 백링크 패널에 A가 자동으로 뜬다. 즉 **일일 → 개념 단방향만으로 양쪽 조회가 다 된다.**

이게 왜 중요하냐면, 반대로 걸었으면 개념 노트 본문이 "2026-07-29에 봄, 2026-08-03에 또 봄..." 같은 시간 로그로 더러워졌을 거다. 지도는 지도대로 깨끗하게 두고 시간 정보만 공짜로 얻는 셈. 링크 방향을 정하는 문제가 사실은 **"어느 노트를 오염시키지 않을 것인가"** 문제였다는 게 의외였다.

**[[종료 훅]]을 게이트로 쓰면 게이트 자체가 장애점이 된다.**

Codex 리뷰 게이트가 stop 훅에 걸려 있었는데, Codex 쪽 지출 한도가 차서 리뷰가 계속 실패했다. 그러자 **턴을 끝내는 것 자체가 막혔다.** 에이전트가 "게이트 끌까요?"라고 물어보려 해도, 그 질문을 하려면 턴을 끝내야 하고, 턴을 끝내려면 게이트를 통과해야 하는 교착.

일반화하면 — **검증 장치를 종료 경로(exit path)에 두면, 검증이 실패했을 때 빠져나갈 길이 같이 막힌다.** 배포 파이프라인의 필수 게이트, 리소스 해제하는 `finally` 블록, 종료 시 flush 하는 로거 전부 같은 모양이다. 그래서 이런 자리엔 보통 **우회 경로(bypass)나 타임아웃**을 같이 설계해 둔다. 설계가 나빴다기보다, 실패 모드를 안 본 것.

**판단 기준이 곧 트리거인 규칙은 지연 로딩에 둘 수 없다.**

카파시 가이드 플러그인이 271세션 동안 0회 호출된 걸 보고 처음엔 규칙이 별로인가 했는데, 아니었다. 스킬은 **호출돼야 읽히는데**, "이 규칙을 쓸 상황인가?"를 판단하려면 규칙이 **이미 읽혀 있어야** 한다. 닭-달걀이라 영원히 안 불린다.

[[FastMCP 대규모 도구의 토큰 절약]]에서 본 지연 로딩은 도구 *설명서*를 창고에 넣는 얘기였다. 도구는 이게 통한다 — "배포 로그 찾아줘"라는 요청 문장 자체가 검색 키워드가 되니까. 그런데 **행동 규칙은 요청 문장에 키워드가 안 나온다.** "커밋해줘"라는 말 어디에도 "커밋 전에 fetch 해라"를 꺼낼 단서가 없다. 그래서 **절차는 지연 로딩, 규칙은 상시 로드**로 갈린다. 일일 노트 캡처를 스킬 대신 상시 가이드로 만든 것도 같은 이유.

**"안 쓴다"는 증거와 "계측이 없다"는 침묵은 다르다.**

하네스를 정리하면서 0을 세 종류로 나눠야 했다. ① 스킬·커맨드처럼 호출 카운터가 있는 것 — 0은 진짜 미사용이다. ② MCP 도구처럼 컨텍스트 비용은 0인데 호출 기록은 남는 것 — 공짜라는 게 유지 근거가 되진 않는다. ③ 테마·출력 스타일처럼 **카운터 자체가 없는 것** — 여기서 0은 미사용이 아니라 **계측 부재**다.

③을 ①로 착각하면 멀쩡히 쓰던 걸 지운다. 일반화하면 **관측되지 않는 것은 "없음"이 아니다.** 대시보드에서 지표가 안 뜨는 것과 값이 0으로 찍히는 것을 구분하는 문제와 같은 모양이다.

**설정을 껐는데 계속 되살아나면, 끄는 곳이 아니라 켜는 곳을 찾아야 한다.**

Codex 리뷰 게이트가 반복해서 돌아온 이유를 찾았다. `/link-harness` 가 프로젝트를 연결할 때마다 `--enable-review-gate` 를 실행하고 있었다. 상태(state)를 고치는 것과, **그 상태를 다시 쓰는 코드**를 고치는 건 다르다. 멱등하게 상태를 덮어쓰는 프로비저닝 스크립트가 있으면 수동 변경은 다음 실행 때 전부 지워진다.

[[컨트롤 루프]]와 정확히 같은 모양이다 — desired state 를 계속 실제 상태에 밀어넣는 것. 다만 쿠버네티스에선 그게 **기능**이고, 여기선 **버그**로 느껴졌다. 차이는 desired state 를 내가 알고 있었느냐뿐이다. 선언형 시스템에서 "왜 내 수동 변경이 자꾸 사라지지?"는 거의 항상 이 모양이라, 앞으로는 **되살아나는 설정을 보면 먼저 선언 출처를 찾는 습관**을 들이자.

**[[MCP]] 서버도 API 서버다 — 다른 건 규약뿐이다.**

오래 걸리는 작업(AI 배너 생성 같은 것)을 MCP 툴로 돌릴 때 "연결을 끊었다 다시 붙여서 폴링하면 되나? MCP 서버는 API 서버도 아닌데?" 하고 물었는데, 전제가 틀렸다. MCP 서버도 그냥 서버 프로세스다. REST 대신 **JSON-RPC 2.0** 을 쓸 뿐이고, 안쪽엔 DB·큐·백그라운드 워커를 얼마든지 붙일 수 있다.

그래서 해법도 REST와 똑같다. 연결을 끊었다 붙이는 게 아니라 **잡을 쪼개서 `job_id` 를 발급**하고, 상태를 연결이 아니라 서버 바깥(DB·Redis)에 둔다. 그러면 **연결 수명과 작업 수명이 분리**된다. 세탁소에서 옷을 맡기고 접수증을 받아 나오는 것과 같은 구조 — 접수증을 발급하는 건 세탁소가 특별한 시스템이어서가 아니라 그냥 장부를 두면 되는 일이다. ([[FastMCP 대규모 도구의 토큰 절약]]이 "무엇을 보여줄지"를 줄이는 얘기였다면, 이건 "얼마나 오래 붙잡을지"를 줄이는 얘기다.)

**재개(resumability)가 살리는 건 이벤트 스트림이지 요청/응답이 아니다.**

Streamable HTTP 에는 실제로 재개 장치가 있다 — `initialize` 때 받은 `Mcp-Session-Id` 를 이후 요청에 붙이고, SSE 이벤트마다 달린 `id` 를 `Last-Event-ID` 헤더로 되돌려주면 끊긴 지점 다음부터 재전송받는다.

그런데 이게 복구하는 건 **스트림**이다. 이미 타임아웃 난 `tools/call` 의 응답은 되살아나지 않는다 — 그 요청은 클라이언트 입장에서 id를 가진 요청 하나이고, 실패로 종결됐기 때문. 나중에 결과가 도착해도 받을 맥락이 없다. **"연결이 복구된다"와 "진행 중이던 작업의 결과를 받는다"는 다른 문제다.** 게다가 stdio transport 면 프로세스가 곧 세션이라 재개 자체가 성립하지 않는다.

## 남은 의문

- 백링크는 링크 텍스트만 보여주는데, "왜 그때 이걸 봤는지" 맥락까지 남기려면 결국 일일 노트에 문장을 써둬야 한다. 그럼 일일 노트가 얼마나 두꺼워져야 적당한가? 지금 3줄 템플릿이 너무 얇을 수도.
- 일일 노트가 쌓이면 그 자체를 훑는 입구(주간·월간 노트?)가 필요해질까. 아니면 검색으로 충분한가. 일단 안 만들고 불편해질 때까지 기다려 보기로.
- 캡처 규칙이 매 세션 380토큰쯤 먹는다. 며칠 써보고 건지는 재료가 그 값을 하는지 봐야 한다. 아무것도 안 걸리면 게이트가 너무 빡센 거고, 잡다한 게 다 걸리면 "세션 마무리" 판정이 헐거운 거다.

# 지수 백오프와 지터

재시도 간격을 **점점 늘리고(백오프), 거기에 무작위를 섞는(지터)** 패턴. [[WebSocket]] 재연결 코드를 뜯어보다 만났는데, 한 줄짜리 관용구로 넘길 게 아니라 **두 개의 다른 문제를 각각 푸는 두 장치**였다.

```js
delay = Math.min(delay * 2, 30_000) + Math.random() * 300;
//      └── 백오프 ──────────────┘   └── 지터 ──────┘
```

## 백오프 — 죽은 서버를 그만 두드린다

고정 간격 재시도가 왜 나쁜지는 서버 입장에서 보면 명확하다. 서버가 과부하로 죽었는데 클라이언트 1,000개가 1초마다 두드리면 **초당 1,000요청이 영원히 유지된다.** 서버는 일어설 틈이 없다. 치료하러 온 사람들이 문 앞을 막아서 의사가 못 들어가는 꼴이다.

간격을 2배씩 늘리면 압력이 지수적으로 빠진다. 0.5초 → 1 → 2 → 4 → 8 → 16 → 30(상한). 상한을 두는 이유는 안 두면 몇 시간짜리 간격이 나와서, 서버가 살아나도 클라이언트가 한참 뒤에나 알아채기 때문이다.

**성공하면 반드시 초기값으로 되돌린다.**

```js
ws.onopen = () => { delay = 500; };
```

이걸 빼먹으면 잠깐 끊겼다 붙는 일이 몇 번 반복된 뒤 재연결 간격이 30초에 눌러앉는다. 정상 동작 중인데 다음 끊김에서 30초를 기다리게 되는, 원인 찾기 어려운 종류의 버그다.

## 지터 — 백오프만으론 못 막는 것

백오프를 제대로 넣어도 남는 문제가 있다. **모두가 같은 시각에 끊겼으면 모두가 같은 시각에 재시도한다.**

```
서버 재시작 → 1,000개 클라이언트 동시 끊김
  0.5초 후 → 1,000개 동시 재시도 → 서버 다시 과부하 → 동시 실패
  1초   후 → 1,000개 동시 재시도 → 또 실패
  2초   후 → ...
```

간격은 늘어나는데 **뭉침이 안 풀린다.** 부하 그래프가 평평해지는 게 아니라 간격만 벌어진 스파이크가 된다. 이게 **thundering herd**(우르르 몰려드는 무리)다.

`Math.random()`이 이 뭉침을 깬다. 각자 다른 시각에 흩어져 도착하니 같은 총량이 시간축에 펴진다. **백오프는 총량을 줄이고, 지터는 그 총량을 고르게 편다** — 목적이 다르니 둘 다 필요하다.

깨달은 김에 되짚으니, [[Long Polling]] 클라이언트의 `catch { await sleep(1000) }`도 똑같이 위험하다. 고정 1초 재시도는 백오프도 지터도 없는 최악의 조합이다.

## 어디서 또 만나나

이게 [[WebSocket]] 전용 관용구가 아니라 **재시도가 있는 곳이면 어디든 나오는 패턴**이라는 게 이 노트를 따로 뺀 이유다.

- **Kubernetes** — Pod이 계속 죽으면 `CrashLoopBackOff` 상태가 된다. 이름에 backoff가 그대로 들어 있고, 재시작 간격을 10초→20초→40초로 늘린다. [[컨트롤 루프]]가 "목표 상태로 계속 되돌린다"고 해서 **무한정 같은 속도로 되돌리지는 않는다**는 뜻이다. 컨트롤 루프 노트를 읽을 때 놓쳤던 디테일.
- **캐시 만료** — 같은 시각에 만료되게 TTL을 주면 만료 순간 전부 DB로 몰린다(cache stampede). TTL에 지터를 섞는 게 정석이다.
- **크론 배치** — 여러 인스턴스가 정각에 도는 것도 같은 문제다.

세 사례가 전부 **"동기화된 다수"가 만드는 스파이크**다. 재시도든 만료든 스케줄이든, 여러 주체가 같은 시각에 같은 행동을 하도록 설계하면 거기서 터진다. 지터는 그 동기화를 일부러 깨는 장치다.

> 상태: #wip — 다음 가지: full jitter vs equal jitter(AWS 아키텍처 블로그의 변형들), 재시도 상한 이후의 처리(포기할 것인가 영원히 시도할 것인가), 서버 쪽에서 미는 백프레셔(`Retry-After` 헤더)와의 역할 분담.

> 왜 여기 붙나: 재시도 총량은 백오프가 줄이고, 그 총량은 지터가 고르게 편다

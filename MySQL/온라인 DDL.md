# 온라인 DDL (Online DDL)

**테이블을 읽고 쓰는 서비스를 멈추지 않고 스키마를 바꾸는 기법.** 옛날 MySQL은 `ALTER TABLE` 한 번에 테이블 전체를 락 걸고 통째로 복사해서, 큰 테이블은 DDL 한 줄이 서비스 장애가 됐다. "온라인"의 목표는 **그 DDL이 도는 동안에도 다른 세션이 INSERT/UPDATE/DELETE를 계속할 수 있게** 하는 것.

핵심은 두 축을 따로 보는 것 — **ALGORITHM(테이블을 얼마나 건드리나)** 과 **LOCK(그동안 동시 접근을 얼마나 막나)**.

## ALGORITHM — 작업의 무게

무거운 순서대로 세 가지. 자세한 건 [[INSTANT DDL]]에서 다뤘고, 여기선 나란히 놓고 본다.

| ALGORITHM | 테이블 데이터 | 언제 |
|---|---|---|
| `COPY` | 임시 테이블에 전 행 복사 후 교체 | 옛 방식 / 다른 게 다 안 될 때 |
| `INPLACE` | 자리에서 재구성(주로 클러스터 인덱스 리빌드) | 인덱스 추가 등 |
| `INSTANT` | **안 건드림, 메타데이터만** | 컬럼 추가/삭제(8.0.29+) 등 |

MySQL은 명시가 없으면 **가능한 가장 싼 쪽부터** 자동 선택한다(INSTANT → INPLACE → COPY). 특정 작업이 어느 알고리즘까지 되는지는 작업 종류(인덱스냐 컬럼이냐 타입변경이냐)에 달렸다.

## LOCK — 그동안 남들은 뭘 할 수 있나

같은 INPLACE라도 동시 접근 허용 범위를 `LOCK` 절로 조절한다.

| LOCK | 읽기 | 쓰기 |
|---|---|---|
| `NONE` | O | O |
| `SHARED` | O | X |
| `EXCLUSIVE` | X | X |

`ALGORITHM=INPLACE, LOCK=NONE`이면 재구성하는 내내 읽기·쓰기가 다 열려 있다 — 이게 우리가 말하는 "온라인"의 이상적 모습. 단 작업 종류에 따라 최소 요구 LOCK이 정해져 있어, 원하는 것보다 강한 락이 강제될 수 있다.

## "온라인이어도 공짜는 아니다"

- INPLACE/COPY는 재구성 중 **임시 로그 공간**과 디스크 I/O를 쓴다. DML이 몰리면 로그가 넘쳐 실패할 수도.
- DDL 시작·끝 순간엔 아주 짧게라도 **메타데이터 락(MDL)**을 잡는다. 그 테이블에 긴 트랜잭션이 걸려 있으면 그 순간 DDL이 대기 → 뒤따르는 쿼리까지 줄줄이 막히는 사고가 여기서 난다.
- 그래서 실무에선 `ALGORITHM=`/`LOCK=`을 **명시**해서, 기대보다 무거운 방식으로 조용히 떨어지지 않고 **에러로 튕기게** 하는 걸 권장.

```sql
-- 인덱스 추가를 온라인으로, 안 되면 에러
ALTER TABLE orders ADD INDEX idx_status (status), ALGORITHM=INPLACE, LOCK=NONE;
```

---

이 모든 게 가능한 밑바탕엔 [[데이터 딕셔너리]]가 있다 — 스키마의 단일 출처가 트랜잭션 안전하게 관리되기에, DDL 중간에 죽어도 스키마가 반쪽 상태로 깨지지 않는다.

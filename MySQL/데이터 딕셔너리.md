# 데이터 딕셔너리 (Data Dictionary)

**DB가 "테이블·컬럼·인덱스가 어떻게 생겼는지"를 스스로 적어두는 시스템 카탈로그.** 사용자 데이터가 아니라 *데이터에 대한 데이터(메타데이터)*를 담는 곳. MySQL 8.0에서 이게 크게 바뀌었고, 그 변화가 [[INSTANT DDL]]·[[온라인 DDL]]이 안전하게 도는 밑바탕이다.

## MySQL 8.0 이전 — 흩어져 있던 메타데이터

옛날 MySQL은 스키마 정보가 여러 곳에 **파일과 테이블로 쪼개져** 있었다.

- 테이블마다 `.frm` 파일 — 컬럼 구조를 담은 별도 바이너리 파일.
- InnoDB는 자기 내부 딕셔너리에도 같은 정보를 또 들고 있었다.

문제는 **이 둘이 어긋날 수 있다**는 것. DDL 도중 서버가 죽으면 `.frm`은 새 구조인데 InnoDB 딕셔너리는 옛 구조로 남는 식으로 **스키마가 반쪽 상태로 깨졌다**. `.frm`은 트랜잭션 보호를 못 받으니까.

## MySQL 8.0 — 트랜잭션형 데이터 딕셔너리

8.0은 `.frm`을 **없애고**, 모든 스키마 정보를 **InnoDB 안의 시스템 테이블들**로 통합했다(`mysql` 스키마의 딕셔너리 테이블 — 숨겨져 있어 직접 못 봄, `information_schema` 뷰로 노출).

의미가 큰 지점:

- **스키마 변경이 트랜잭션이 됨** → DDL이 InnoDB 트랜잭션·리두 로그의 보호를 받는다. 중간에 죽어도 원자적으로 커밋 or 롤백 → 반쪽 스키마가 안 생긴다. `.frm` 시절의 그 사고가 사라진 것.
- **단일 출처(single source of truth)** → 파일 하나, 딕셔너리 하나로 정보가 갈라지지 않는다.

## INSTANT/온라인 DDL과의 연결

[[INSTANT DDL]]이 "행에 버전을 달고 읽기 시점에 통역"할 수 있는 이유가 여기 있다 — **버전별 컬럼 배치도가 이 딕셔너리에 살기 때문**. 물리 행은 옛 모양 그대로 두고, 스키마의 진실은 딕셔너리가 들고 있다가 읽을 때 맞춰준다.

[[온라인 DDL]]도 마찬가지 — 딕셔너리가 트랜잭션 안전하니, DDL이 도는 도중에 스키마가 결코 어중간한 상태로 관측되지 않는다.

> 참고: Oracle에도 데이터 딕셔너리가 있지만(그 SGA의 dictionary cache 등), MySQL 8.0의 변화는 특히 "메타데이터 저장을 InnoDB 트랜잭션 엔진 위로 올렸다"는 점이 요지.

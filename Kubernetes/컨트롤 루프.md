# 컨트롤 루프

[[Kubernetes]]의 심장. "심장"이라고 부른 이유는, 선언형이라는 발상이 *실제로 굴러가게* 만드는 게 이 루프 하나이기 때문이다. 한 문장으로: **원하는 상태(desired)와 실제 상태(actual)의 차이를 관찰하고, 그 차이를 좁히는 행동을 하고, 다시 관찰한다 — 무한히.**

이 관찰→차이→행동의 반복을 **reconciliation(수렴)** 이라 부른다.

## desired ↔ actual, 두 개의 상태

모든 k8s 오브젝트는 두 부분을 갖는다.

- **spec** — 내가 선언한 *원하는 상태*. "replicas: 3" 같은 것. etcd에 저장돼 있고, 사람이 `kubectl apply`로 바꾼다.
- **status** — 컨트롤러가 관찰한 *실제 상태*. "지금 2개 떠 있음". 사람이 아니라 시스템이 채운다.

컨트롤러가 하는 일은 결국 `spec == status`가 되도록 미는 것. spec에 3이라 적혀 있는데 status가 2면, 1개를 더 띄우는 행동을 하고, 다시 관찰해서 3이 되면 손을 뗀다. 장애로 하나 죽어 다시 2가 되면? 루프가 또 감지해서 또 띄운다. **자가 복구(self-healing)가 마법이 아니라 이 루프의 당연한 부산물**이라는 게 핵심.

## 컨트롤러 — 리소스 타입 하나당 루프 하나

k8s에는 단일 거대 루프가 있는 게 아니라, **리소스 타입마다 전담 컨트롤러**가 있고 각자 자기 루프를 돈다.

- ReplicaSet controller — "Pod가 N개인가" 만 본다.
- [[Deployment]] controller — "원하는 버전의 ReplicaSet이 있고, 롤아웃이 끝났나" 를 본다.
- Node controller — "노드가 살아있나, 죽었으면 그 위 Pod를 어떻게 하나" 를 본다.

이들이 모여 사는 곳이 [[Kubernetes|Control Plane]]의 **kube-controller-manager**. 각 컨트롤러는 서로를 직접 호출하지 않는다 — 오직 API Server를 통해 상태를 읽고 쓸 뿐. Deployment controller가 ReplicaSet 오브젝트를 만들어 놓으면, ReplicaSet controller가 그걸 보고 Pod를 만든다. 명령 전달이 아니라 **상태를 남기면 다음 컨트롤러가 반응하는** 계주 구조.

## level-triggered — k8s 견고함의 뿌리

여기가 제일 중요한 설계 결정이다. 컨트롤러가 반응하는 방식엔 두 가지가 있다.

- **edge-triggered** — "변화 이벤트"에 반응. "Pod가 죽었다"는 이벤트를 받고 행동. → 이벤트를 *놓치면* 영영 처리 못 한다.
- **level-triggered** — 이벤트가 아니라 *현재 상태 그 자체*를 보고 판단. "지금 2개네, 3이어야 하는데" → 행동.

k8s는 **level-triggered**다. 그래서 컨트롤러가 잠깐 죽었다 살아나 이벤트를 몇 개 놓쳐도 상관없다. 되살아나서 현재 상태를 다시 관찰하면, 놓친 것과 무관하게 "지금 뭐가 틀어졌지?"부터 다시 계산한다. **놓친 이벤트가 누적되어 시스템이 영구히 어긋나는 일이 없다** — 이 견고함이 level 기반에서 나온다.

> 여기서 [[이벤트 루프와 코루틴]]과 대조하면 개념이 선명해진다. 파이썬 이벤트 루프는 *할 일 큐*를 도는 edge 성격(준비된 Task를 꺼내 처리)에 가깝다. k8s 컨트롤 루프는 큐를 비우는 게 목적이 아니라 *상태를 수렴*시키는 게 목적이다. 둘 다 "루프"지만, 하나는 이벤트를 소비하고 하나는 상태를 좁힌다. 같은 단어 안에 다른 철학이 들어 있는 셈.

## watch — 매번 전수조사하지 않으려고

"현재 상태를 계속 관찰한다"면, 1초마다 API Server에 "지금 Pod 몇 개야?"를 폴링해야 할까? 그건 너무 비싸다. 그래서 컨트롤러는 API Server의 **watch**를 구독한다 — 변화가 생기면 API Server가 밀어준다. 그 변화를 로컬 캐시(informer)에 반영해 두고, 컨트롤러는 이 캐시를 상태로 삼아 reconcile한다.

주의: watch(이벤트 스트림)를 쓰지만 철학은 여전히 level 기반이다. watch는 "매번 전수조사를 피하는 성능 최적화"일 뿐, 이벤트를 놓쳐도 주기적 재동기화(resync)로 현재 상태 전체를 다시 훑는다. 이벤트는 *힌트*고, 진실은 언제나 *현재 상태*.

## 그래서 선언형이 가능하다

[[Kubernetes]] 진입 노트에서 "명령형이 아니라 선언형"이라 했던 게 이 루프 위에서 성립한다. 사용자는 spec(원하는 상태)만 선언하고 떠나면 된다. "어떻게 거기 도달할지"의 절차는 컨트롤러가 현재 상태와 비교하며 매 순간 다시 계산한다. 절차를 지시하는 게 아니라 목표를 선언하는 것 — 그 목표를 현실로 유지하는 엔진이 컨트롤 루프다.

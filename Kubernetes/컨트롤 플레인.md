# 컨트롤 플레인

[[Kubernetes]] 클러스터의 "뇌". Worker Node가 실제로 컨테이너를 돌리는 "몸"이라면, *무엇이 어떻게 돌아야 하는지 결정하고 상태를 보관하는* 게 Control Plane. 핵심 통찰 하나: **모든 것이 API Server라는 유일한 정문을 통한다.**

## 네 컴포넌트

- **API Server** — 모든 요청의 관문. `kubectl`도, 내부 컴포넌트도 전부 여기로만 소통한다. 유일한 정문.
- **etcd** — 모든 상태를 저장하는 key-value 저장소. "선언된 상태"가 실제로 사는 곳 = 진실(source of truth).
- **Scheduler** — 새 [[Pod]]를 *어느 노드*에 올릴지 결정.
- **Controller Manager** — [[컨트롤 루프]]들이 모여 도는 곳.

## 왜 다 API Server를 통하나 — 허브 앤 스포크

컴포넌트끼리 **서로 직접 호출하지 않는다.** 오직 API Server를 통해 상태를 읽고 쓸 뿐. 이 한 가지 규칙이 여러 이득을 낳는다.

- **인증·인가·검증을 한 곳에서** — 모든 변경이 정문 하나를 지나니 거기서 다 거른다.
- **etcd 접근 창구 단일화** — etcd에 직접 붙는 건 API Server뿐. 상태 일관성이 지켜진다.
- **결합 제거** — [[컨트롤 루프]]에서 본 "상태를 남기면 다음 컨트롤러가 반응하는 계주"가 이 구조 덕에 성립한다. Deployment 컨트롤러가 ReplicaSet 오브젝트를 API Server에 써두면, ReplicaSet 컨트롤러가 그걸 보고 반응한다. 서로를 몰라도 된다.

명령이 위→아래로 흐르는 게 아니라, 각자 API Server의 상태를 보고 각자 수렴시키는 구조 — [[Kubernetes]] 진입 노트의 그 그림이 여기서 나온다.

## etcd = 진실이 사는 곳

etcd가 곧 클러스터의 "원하는 상태" 전부다. 여기가 죽으면 클러스터는 자기가 뭘 원했는지 잃는다(뇌사). 그래서 보통 홀수 대로 복제해 합의(Raft)로 굴린다. spec을 바꾼다는 건 결국 etcd의 값을 바꾸는 것이고, [[컨트롤 루프]]는 그 값을 진실로 삼아 현실을 맞춘다.

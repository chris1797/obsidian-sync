# HPA

Horizontal Pod Autoscaler. [[Deployment]] 의 `replicas` 를 사람 대신 조절하는 또 하나의 [[컨트롤 루프]]다. 관찰 → 차이 → 행동이 여기선 **"사용률 관찰 → 목표와 비교 → 파드 수 조정"** 이 된다.

## 사용률의 분모는 requests

HPA 가 보여주는 `current / target = 200% / 70%` 의 퍼센트는 노드 CPU 대비가 아니다. **파드의 CPU requests 대비**다([[리소스 requests와 limits]]).

```
requests 350m, 실제 700m 사용 → 200%
```

그래서 requests 를 바꾸면 같은 부하에서도 숫자가 바뀐다. 200% 가 늘 나온다면 "과부하" 일 수도, "requests 가 현실보다 낮음" 일 수도 있다. limits 가 requests 의 2배인데 200% 라면 전자 — 천장에 붙은 것이다([[CPU throttling]]).

## desired 계산식

```
desired = ceil( 현재 파드 수 × 현재 사용률 / 목표 사용률 )
        → [minReplicas, maxReplicas] 로 자른다
```

| 파드 | 현재 | 목표 | 계산 | desired |
|---|---|---|---|---|
| 7 | 200% | 70% | ceil(7×2.86)=20 | **7** (max 에 막힘) |
| 7 | 200% | 60% | ceil(7×3.33)=24 | **7** |
| 7 | 43% | 70% | ceil(7×0.61)=5 | 5 (단, 아래 안정화) |

위 두 줄이 교훈이다. **max 에 막혀 있으면 목표를 60→70 으로 바꿔도 아무 일도 안 일어난다.** 목표를 올리는 건 "덜 늘리겠다" 는 방향이라 오히려 반대이기도 하다.

## 흔들리지 않게 하는 장치 둘

- **tolerance(±10%)** — 현재/목표 비율이 0.9~1.1 이면 조정하지 않는다. 목표 70% 면 63~77% 는 "그대로".
- **스케일다운 안정화(기본 5분)** — 줄이는 건 최근 5분간의 desired 중 최댓값을 따른다. 부하가 잠깐 빠졌다고 바로 줄였다가 다시 늘리는 출렁임을 막는다. 늘리는 건 빠르고 줄이는 건 느린 비대칭.

`behavior` 필드로 이 속도를 직접 조정할 수 있는데 1.18+ 다 — 오래된 클러스터에선 기본값에 묶인다.

## min 은 시작 개수가 아니다

`minReplicas: 5` 인데 배포 직후 7개가 뜨는 걸 보고 헷갈렸다. min 은 **바닥**일 뿐이다. `replicas` 값은 HPA 가 관리하고, 새 배포는 그 값을 **이어받는다.** 롤링 업데이트는 "지금 7개" 를 새 버전 7개로 교체할 뿐.

```
배포 전   HPA 가 replicas=7 로 맞춰 둠
배포      새 ReplicaSet 이 7 을 물려받음 → 7개 교체
배포 후   7/7. 줄일 이유가 생겨도 5분 안정화 동안 보류
```

배포 템플릿이 매번 `replicas: 5` 를 써 넣으면 배포 직후 5로 떨어졌다가 HPA 가 다시 올리는 출렁임이 생긴다. HPA 를 쓰면 매니페스트에서 replicas 를 빼는 이유가 이것.

## max 를 올리기 전에

파드 하나 = requests 만큼의 장부 자리. max 를 7→10 으로 올리는 건 **노드에 requests × 3 (+ 배포 surge 분)의 자리가 있다는 가정**이다. 자리가 없으면 HPA 가 늘려도 새 파드는 Pending 이다. HPA 는 파드 수를 정할 뿐, 자리를 만들어주진 않는다.

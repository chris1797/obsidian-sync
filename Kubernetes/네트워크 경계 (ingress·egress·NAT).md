# 네트워크 경계 (ingress·egress·NAT)

클러스터를 **건물**로 보면, 이 노트가 다루는 건 딱 하나다 — **패킷이 건물 문을 넘을 때 주소가 어떻게 바뀌는가.** inbound·egress·proxy·NAT 는 따로 노는 용어가 아니라, 이 "경계 통과" 한 흐름을 방향별로 부르는 이름일 뿐이다. 그래서 핵심 축은 **방향(direction)** 이다.

| 개념 | 방향 | 비유 |
|---|---|---|
| **inbound / ingress** | 외부 → 클러스터 | 손님이 정문으로 들어옴 |
| **egress** | 클러스터 → 외부 | 직원이 밖으로 나감 |
| **proxy** | (둘 다) | 문 앞에서 대신 전달하는 대리인 |
| **egress NAT IP** | 나갈 때 | 나가는 직원이 드는 건물 대표 명함 |

## 들어오는 쪽 — inbound (ingress)

외부에서 클러스터 *안으로* 오는 요청. 밖에서 [[Pod]]를 직접 부를 수 없다는 게 출발점이다 — Pod IP 는 사설이고 재배포마다 바뀌는 소모품이라([[Pod]] 노트 참조) 외부가 신뢰할 주소가 못 된다. 그래서 층을 세워 숨긴다.

```
외부 사용자 → [LoadBalancer / Ingress] → [Service] → [Pod]
             (정문 안내데스크)          (고정 별명)   (실제 일꾼)
```

[[Service]]가 "바뀌는 Pod 를 고정 이름 뒤에 숨긴다"까지였다면, **Ingress 는 그 앞단의 L7(HTTP) 안내데스크**다 — "`/api` 는 이 Service, `/admin` 은 저 Service" 처럼 도메인·경로를 보고 어느 Service 로 넘길지 결정. Service 노트에서 "다음 가지: Ingress" 라 적어둔 그 자리가 여기다.

## 대리인 — proxy (방향에 따라 이름이 갈린다)

**대리인**이다. A 가 B 한테 직접 안 가고 중간의 P 가 대신 전달. *어느 방향을 대신하느냐* 로 종류가 갈린다.

- **reverse proxy** (들어오는 쪽) — 손님은 P 를 진짜 서버로 안다. P 가 뒤의 실제 서버로 넘긴다. **Ingress 컨트롤러(nginx 등)가 이것.** 손님으로부터 내부를 *숨김*.
- **forward proxy** (나가는 쪽) — 내부에서 밖으로 나갈 때 P 를 거쳐 나간다. 상대는 P 만 본다. egress 게이트웨이가 이 성격.
- **kube-proxy** — 이름만 proxy, 결이 다르다. [[Service]] 가상 IP 로 온 패킷을 살아있는 Pod 로 넘기는 *노드 내부 라우팅 규칙*(iptables/IPVS)이다. 경계를 넘는 대리가 아니라 내부 배달부.

## 나가는 쪽 — egress NAT IP (여기가 핵심)

**NAT(Network Address Translation)** = 패킷이 경계를 넘을 때 주소를 바꿔치기. 나가는 방향에서 *출발지* 를 바꾸는 게 **SNAT(Source NAT)**.

왜 필요한가는 중간 상태를 따라가면 또렷하다.

```
[Pod: 10.2.7.33]   ← 사설 IP, 재배포마다 바뀜, 외부에서 신뢰 불가
      │  외부 API(예: 결제사) 호출
      ▼
[egress 게이트웨이] ← 여기서 SNAT: 출발지를 203.0.113.10 으로 치환
      ▼
[상대 방화벽]      ← "203.0.113.10 은 허용 목록에 있음" → 통과
```

- Pod IP 는 사설이라 밖에선 의미 없고, 재배포하면 바뀐다.
- 상대 방화벽이 "이 IP 만 받겠다" 하려면 우리 쪽 **출발지 IP 가 고정**이어야 한다.
- 그래서 나가는 트래픽을 게이트웨이에서 **고정된 egress IP 하나로 SNAT**. 상대는 개별 Pod 가 아니라 그 *대표 IP* 만 본다 → 그 IP 를 상대가 allowlist 에 등록.

이게 사내 [[ACL]]·방화벽 요청 폼의 "출발지 IP" 칸에 **egress NAT IP 를 적는 이유**다. Pod IP 를 적으면 배포 때마다 바뀌어 등록이 무용지물이 된다. 그리고 이 "출발지 → 목적지, 허용" 이라는 방향성이 [[ACL]] 자체의 방향 개념과 그대로 포개진다.

## 한 번에 보기

방향이 곧 이름을 정한다 — 들어오면 ingress(안내데스크가 reverse proxy), 나가면 egress(대표 명함이 SNAT). 둘 다 공통 동기는 하나다: **소모품인 [[Pod]] 를 안정된 무언가(고정 이름 / 고정 IP) 뒤에 숨긴다.** [[Service]]가 안쪽에서 한 일을, 경계에서 다시 한 번 하는 셈.

# Kubernetes

컨테이너를 **여러 대의 서버에 걸쳐, 원하는 상태로 계속 유지시키는** 오케스트레이션 시스템. 그런데 "컨테이너 관리 도구"라고만 이해하면 핵심을 놓친다. k8s의 뿌리 발상은 하나다 — **너는 원하는 상태(desired state)를 선언하고, k8s는 현재 상태를 거기에 끊임없이 맞춘다.** SSH를 이해하는 게 곧 [[SSH|공개키 비대칭성]]을 이해하는 것이었듯, k8s를 이해하는 건 이 *선언형 + 자동 수렴* 모델을 이해하는 것과 거의 같다.

## 왜 오케스트레이션인가 — docker run이 안 되는 지점

컨테이너 하나 띄우는 건 `docker run` 한 줄이면 된다. 문제는 규모다.

- 컨테이너가 죽으면? 누가 다시 띄워야 한다.
- 트래픽이 몰리면? 같은 컨테이너를 여러 개로 늘려야(scale) 한다.
- 서버(노드) 한 대가 통째로 죽으면? 그 위에서 돌던 것들을 살아있는 노드로 옮겨야 한다.
- 새 버전을 배포하는데 무중단으로? 조금씩 갈아끼우고, 문제 생기면 되돌려야(rollback) 한다.

이걸 컨테이너 수십~수백 개 × 서버 여러 대 규모에서 **사람이 손으로** 하는 건 불가능하다. 오케스트레이션은 이 "계속 지켜보고 원하는 상태로 되돌리는" 일을 자동화한다.

## 뿌리 발상 — 명령형이 아니라 선언형

여기서 발상의 전환이 갈린다. 보통 우리가 쓰는 방식은 **명령형**이다: "컨테이너를 켜라", "하나 더 띄워라", "이건 꺼라" — 하나하나 지시.

k8s는 **선언형**이다. "이 앱은 항상 3개 떠 있어야 해"라고 *상태를 선언*만 한다. 어떻게 3개를 유지할지는 k8s가 알아서 한다. 하나가 죽어 2개가 되면, k8s가 그걸 감지하고 1개를 새로 띄워 3개로 되돌린다.

이 "선언된 상태 ↔ 실제 상태의 차이를 계속 좁히는" 반복이 [[컨트롤 루프|control loop (reconciliation)]]다. k8s의 심장. 이 루프가 쉼 없이 도는 덕에, 장애가 나도 사람이 개입하지 않고 시스템이 스스로 원하는 모습으로 복구된다.

## 큰 그림 — Control Plane과 Worker Node

클러스터는 두 종류의 노드로 나뉜다.

**Control Plane** — 클러스터의 "뇌". 무엇이 어떻게 돌아야 하는지 결정한다.
- **API Server** — 모든 요청의 관문. `kubectl`도, 내부 컴포넌트도 전부 여기를 통해서만 소통한다. 유일한 정문.
- **etcd** — 클러스터의 모든 상태를 저장하는 key-value 저장소. "선언된 상태"가 실제로 사는 곳. 여기가 곧 진실(source of truth).
- **Scheduler** — 새로 뜰 [[Pod]]를 *어느 노드*에 올릴지 결정.
- **Controller Manager** — 위에서 말한 [[컨트롤 루프]]들이 도는 곳. 실제 상태를 원하는 상태로 수렴시키는 일꾼.

**Worker Node** — 실제로 컨테이너가 도는 곳. "몸".
- **kubelet** — 노드마다 하나. API Server가 시킨 대로 그 노드에서 컨테이너를 띄우고 상태를 보고.
- **kube-proxy** — 노드의 네트워크 규칙을 관리 ([[Service]] 트래픽 라우팅).
- **container runtime** — 실제 컨테이너를 실행하는 엔진(containerd 등). Docker에서 쓰던 그 층.

흐름을 한 줄로: `kubectl apply` → **API Server**가 받아 **etcd**에 저장 → **Controller/Scheduler**가 "떠야 할 게 안 떠 있네" 감지 → 노드 배정 → 그 노드의 **kubelet**이 실제로 컨테이너 실행. 명령이 위→아래로 흐르는 게 아니라, 각 컴포넌트가 etcd의 상태를 보고 각자 수렴시키는 구조라는 게 포인트.

## 핵심 오브젝트의 계층

k8s에서 "무언가를 배포한다"는 건 결국 오브젝트(YAML)를 선언하는 것. 자주 만나는 것들이 층을 이룬다.

- **[[Pod]]** — 배포의 최소 단위. 컨테이너 1개(보통) + 공유 네트워크/스토리지. k8s는 컨테이너가 아니라 Pod를 다룬다.
- **ReplicaSet** — "Pod를 N개 유지" 담당. 하지만 이걸 직접 쓰는 일은 드물다.
- **[[Deployment]]** — ReplicaSet 위에 얹혀 *버전 롤아웃·롤백*까지 관리. 실무에서 앱 배포는 거의 이걸로 한다.
- **[[Service]]** — Pod는 죽고 살면서 IP가 계속 바뀐다. 이 흔들리는 Pod들 앞에 고정된 진입점을 세워 발견(discovery)·로드밸런싱을 해주는 층.
- **ConfigMap / Secret** — 설정값·비밀값을 이미지와 분리해 주입.
- **Namespace** — 클러스터를 논리적으로 쪼개는 칸막이.

## 실제 배포에서 보는 계층

배포 대시보드에서 마주치는 한 줄 — `[ASKOR_HNB01] K8S-ENV-SERVER-003 / namespace: aim` — 을 뜯으면 이 중첩이 그대로 드러난다.

![[k8s 배포 계층.svg]]

- **Region/사이트** (`ASKOR_HNB01`) — 클러스터가 물리적으로 어느 데이터센터에 사는가.
- **Cluster** (`K8S-ENV-SERVER-003`) — 완결된 k8s 한 세트([[컨트롤 플레인]] + Worker Node).
- **Namespace** (`aim` / `aim-qa`) — 클러스터를 논리적으로 쪼갠 칸막이. 운영(REAL)과 QA가 *같은 클러스터*에 namespace로만 갈려 공존하기도 하는데, 이게 "격리가 물리적이 아니라 논리적"임을 보여주는 장면이다. (운영에 QA 부하가 샐 여지가 있는 트레이드오프.)
- **[[Pod]]** — 그 안에 도는 실제 워크로드. 운영 배포엔 보통 보안 검토(Security JIRA) 같은 게이트가 걸린다.

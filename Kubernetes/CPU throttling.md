# CPU throttling

CPU limits 를 넘으면 파드가 죽는 줄 알았다. 아니다 — **느려진다.** [[리소스 requests와 limits]]의 limits 가 커널에서 어떤 모양이 되는지 보면 왜 그런지 보인다.

## 100ms 마다 충전되는 교통카드

limits 는 리눅스 CFS 의 bandwidth control 로 바뀐다.

```
limits 700m = 0.7 CPU
구간(period) = 100ms            (기본값)
쿼터(quota)  = 0.7 × 100ms = 70ms
cgroup v2: cpu.max = "70000 100000"
```

100ms 마다 CPU 시간 70ms 가 충전된다. 다 쓰면 카드가 막히고, 구간이 끝날 때까지 컨테이너의 모든 스레드가 **실행 불가.** 남은 시간은 이월되지 않는다.

## 쿼터는 모든 코어의 합이다

여기서 헷갈렸다. 700m 은 "코어 0.7개" 가 아니라 **"CPU 시간 70ms"** 다.

```
스레드 1개:  [   실행 70ms   ][멈춤 30ms]
스레드 4개:  [4개 동시 17.5ms][     모두 멈춤 82.5ms      ]
              4 × 17.5 = 70ms 를 순식간에 소진
```

그래서 1400m 이면 한 구간에 140ms 를 쓸 수 있다 — 100ms 보다 길 수 있는 건 여러 코어에서 동시에 쓴 시간의 합이라서.

## 평균이 낮아도 걸린다

두 번째 그림이 함정이다. 1초 평균으로 보면 사용률이 여유 있어 보여도, 요청이 몰리는 순간 쿼터를 다 쓰고 수십 ms 씩 멈춘다. 그 사이 들어온 요청은 다 줄을 서고 p95/p99 가 튄다. **평균 사용률 그래프에는 안 보이고**, throttling 지표로만 보인다.

```promql
rate(container_cpu_cfs_throttled_periods_total[5m])
  / rate(container_cpu_cfs_periods_total[5m])
```

거꾸로, 사용률이 "requests 의 200%" 로 찍히는데 limits 가 requests 의 2배라면 — 평균적으로 천장에 붙어 있다는 뜻이다. 이때 보이는 숫자는 실제 수요가 아니라 **천장에 막힌 값**이라, 진짜 수요는 그 이상일 수 있다.

## 파이썬 단일 프로세스라면

[[GIL]] 때문에 파이썬 프로세스 하나는 사실상 코어 1개(1000m) 이상을 못 쓴다. 이 경우 limits 를 1400m 으로 올려도 400m 은 대부분 논다. 위의 "스레드 4개" 그림도 잘 안 맞고, 이벤트 루프 하나가 쿼터를 쓰는 모양에 가깝다. 파드를 키우기보다 **개수를 늘리는 쪽**([[HPA]])이 맞는 앱이다.

## limits 를 아예 빼면?

많이 쓰는 선택지이고 근거도 있다.

- 좋아지는 것: throttling 이 사라지고, 노드가 한가할 때 남는 CPU 를 끝까지 쓴다.
- 이웃이 굶는 문제는 생각보다 작다: 경합 시엔 requests 비율로 나누니 남들도 자기 몫은 되찾는다.
- 나빠지는 것: 성능이 이웃 상태에 따라 출렁인다. requests 가 낮으면 평소엔 빌려 쓰다가 붐비는 날 갑자기 바닥으로 떨어진다. 그리고 쿼터가 없으면 JVM·Go 같은 런타임이 노드 전체 코어 수를 보고 스레드를 과하게 띄울 수 있다.
- 전제: requests 가 실제 사용량에 맞게 잡혀 있어야 하고, 네임스페이스 쿼터·LimitRange 가 허용해야 한다.

**메모리 limits 는 예외 없이 유지** — 메모리는 멈춰서 조절할 수 없어서 OOM 으로 끝난다.

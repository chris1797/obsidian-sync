# Deployment

[[Pod]]은 소모품이라 혼자선 "N개 유지"도 "무중단 교체"도 못 한다. 그 위에 얹혀 *버전 롤아웃·롤백*까지 지휘하는 게 Deployment. 실무에서 앱 배포는 거의 이걸로 한다. 한 문장: **"이 이미지를 N개 띄워라, 바꿀 땐 무중단으로"를 선언하면, 나머지 절차는 [[컨트롤 루프]]가 알아서 굴린다.**

## 3층 구조 — Deployment ▷ ReplicaSet ▷ Pod

Deployment가 Pod를 직접 만들지 않는다. 한 겹을 더 둔다.

- **Deployment** — 버전·롤아웃·롤백 담당
- **ReplicaSet** — "Pod를 N개 유지"만 담당 (직접 쓸 일은 드묾)
- **[[Pod]]** — 실제 실행 단위

원하는 버전마다 ReplicaSet을 하나 만들고, 그 ReplicaSet이 Pod를 N개 찍어낸다. 버전을 바꾸면? **새 ReplicaSet을 만들어 그 Pod를 늘리면서, 옛 ReplicaSet의 Pod를 줄인다.** 이 "새 RS 늘리고 옛 RS 줄이기"가 롤링 업데이트의 뼈대다.

## 롤링 업데이트 — 무중단의 실제

v1 3개에서 v2로 바꿀 때, 상태는 이렇게 흐른다.

```
[v1][v1][v1]              현재
[v1][v1][v1][v2:생성]      새 v2 먼저 띄움 → "준비됨(ready)" 기다림
[v1][v1][v2✓]            준비되면 그때 옛 v1 하나 버림
[v1][v2✓][v2✓]           반복…
[v2✓][v2✓][v2✓]          전부 교체
```

핵심은 **항상 서비스 가능한 수를 유지**한다는 것 — 낡은 걸 먼저 죽이는 게 아니라, 새 걸 띄워 건강을 확인한 뒤 낡은 걸 버린다. 그래서 사용자는 교체를 못 느낀다(무중단). "얼마나 앞서 띄우고(maxSurge), 얼마나 부족해도 되나(maxUnavailable)"로 속도를 조절한다.

## 롤백이 빠른 이유 — 옛 ReplicaSet을 안 지운다

Deployment는 옛 ReplicaSet을 곧장 삭제하지 않고 **리비전 히스토리로 남겨둔다.** 그래서 새 버전에 문제가 생기면, 옛 RS의 Pod를 다시 늘리는 것만으로 즉시 되돌아간다. 새로 빌드·배포하는 게 아니라 *이미 있던 것*을 되살리는 거라 빠르다.

## 다시, 선언형

`image: v2`로 **spec만 바꾸면** [[컨트롤 루프]]가 현재 상태(v1)와 비교해 위 절차를 매 순간 다시 계산한다. 내가 "이렇게 저렇게 갈아끼워"라고 절차를 지시하는 게 아니라 "최종은 v2 3개"라고 목표만 선언 — [[Kubernetes]] 지도의 "명령형이 아니라 선언형"이 실제로 벌어지는 장면.

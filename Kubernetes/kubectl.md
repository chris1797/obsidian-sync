# kubectl

[[Kubernetes]] 클러스터에 말을 거는 커맨드라인 클라이언트. 그런데 "k8s 명령어 도구"라고만 보면 위치를 놓친다. [[컨트롤 플레인]] 노트의 핵심 문장 — *모든 것이 API Server라는 유일한 정문을 통한다* — 에서 **kubectl은 사람이 그 정문을 두드리는 창구**다. 내부 컴포넌트(kubelet, 컨트롤러)와 정확히 같은 문으로 들어간다. 특권 통로가 따로 있는 게 아니다.

그래서 kubectl로 할 수 있는 일의 범위 = API Server가 허용하는 범위이고, 권한(RBAC)도 거기서 갈린다. 읽기만 되는 계정이면 `get`·`logs`는 되고 `delete`는 막힌다.

## 명령이 아니라 상태 제출

가장 헷갈렸던 지점. `kubectl apply -f app.yaml` 은 "이걸 실행해라"라는 **명령이 아니다.** "이 앱은 이런 모습이어야 한다"는 **선언을 제출**하는 것이다. 제출된 상태는 etcd에 저장되고, 실제로 그 모습을 만드는 건 [[컨트롤 루프]]다.

이 차이가 실감나는 순간이 있다. 파드를 `delete` 해도 곧 다시 뜬다. 명령형 사고로는 "지웠는데 왜 살아나지?"지만, 선언형에서는 당연하다 — *지운 건 현재 상태고, 선언된 상태는 그대로*라서 루프가 다시 채워 넣는다. 진짜로 없애려면 선언(Deployment)을 지워야 한다.

반대로 `get`·`logs`처럼 읽기만 하는 명령은 선언과 무관하게 그냥 현재 상태를 조회한다.

## 네 갈래로 나눠 기억하기

**① 보기 — 진단의 출발점**

```
kubectl get pods            # 뭐가 떠 있나, 몇 번 재시작했나
kubectl describe pod <이름>  # 그 하나의 상세 + 최근 Events
```

`describe` 출력에서 정작 중요한 건 맨 아래 **Events**다. "왜 안 뜨지?"의 답이 거의 거기 있다.

```
Warning  Failed    ImagePullBackOff    이미지를 못 받아옴
Warning  BackOff   CrashLoopBackOff    떴다 죽었다 반복
```

`get`이 "지금 상태 스냅샷"이라면 `describe`는 "여기까지 오게 된 사연"이다. 상태만 보고 원인을 추측하지 말 것.

**② 로그**

```
kubectl logs -f <파드>          # 실시간
kubectl logs --previous <파드>   # 죽기 직전 컨테이너의 로그
```

`--previous`가 결정적이다. 재시작한 파드는 **현재 컨테이너 로그에 죽은 이유가 없다.** 죽은 건 이전 컨테이너이기 때문. `CrashLoopBackOff`를 만나면 반사적으로 이걸 봐야 한다.

**③ 안으로 들어가기**

```
kubectl exec -it <파드> -- sh              # 파드 안에서 명령 실행
kubectl port-forward svc/<서비스> 8080:80   # 로컬 포트 ↔ 클러스터 내부 연결
```

`port-forward`가 특히 쓸모 있다. 내 로컬 `localhost:8080`을 클러스터 안 서비스에 직결해준다. [[네트워크 경계 (ingress·egress·NAT)]]의 ingress 층을 **통째로 우회**하므로, 외부에서 접근이 막혀 있을 때 "앱 자체는 멀쩡한가 / 경계에서 막힌 건가"를 가르는 데 쓴다. 실제로 외부 호출이 403으로 막혔을 때, 이걸로 안에서 찔러보면 앱 문제인지 방화벽·ACL 문제인지 즉시 갈린다.

`exec`도 진단용으로 유용하다. 파드 안에서 밖으로 요청을 날려보면 그 파드가 **나갈 때 어떤 주소로 보이는지**(egress) 확인할 수 있다.

**④ 바꾸기**

```
kubectl rollout restart deploy/<이름>   # 재기동
kubectl rollout undo    deploy/<이름>   # 직전 버전으로 롤백
kubectl scale deploy/<이름> --replicas=3
```

[[Deployment]]가 관리하는 롤아웃을 사람이 트리거하는 층이다. 여기서 배운 것 하나: **환경변수를 바꿔도 이미 떠 있는 파드에는 반영되지 않는다.** 환경변수는 컨테이너가 뜰 때 읽히므로, 새 파드가 떠야 한다. 설정을 고쳤는데 그대로면 `rollout restart`를 의심할 것.

## `-n` 을 빼먹는 사고

kubectl은 명령마다 "지금 어느 클러스터의 어느 네임스페이스"를 본다. 네임스페이스를 안 적으면 기본값(`default`)을 보는데, 실제 워크로드는 다른 네임스페이스에 있는 경우가 대부분이라 **아무것도 안 나온다.** 더 위험한 건 클러스터를 착각한 채 `delete`를 치는 쪽이다.

이 "지금 어디를 보고 있는가"를 관리하는 게 [[kubeconfig 와 컨텍스트]]다. kubectl을 안전하게 쓰는 문제의 절반은 사실 그쪽에 있다.

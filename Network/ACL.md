# ACL

**Access Control List** — "누가 어디로 가는 걸 허용/거부할지" 를 한 줄씩 적어 둔 규칙 목록. 방화벽 정책의 알맹이가 이것이다.

한 줄의 모양이 개념 전부를 담고 있다.

```
출발지        →  목적지        : 포트/프로토콜  :  동작
203.0.113.10 →  10.20.0.5     : 443/tcp       :  허용
any          →  10.20.0.5     : any           :  거부   ← 보통 맨 아래 암묵적으로
```

## 방향이 먼저다

[[네트워크 경계 (ingress·egress·NAT)]] 가 "패킷이 문을 넘을 때 주소가 어떻게 바뀌는가" 를 방향 축으로 풀었는데, ACL 은 같은 축을 **허가**로 푼다. 출발지와 목적지를 뒤집으면 완전히 다른 규칙이다 — "A 에서 B 로 가도 된다" 가 "B 에서 A 로 와도 된다" 를 뜻하지 않는다.

그래서 방화벽 요청을 넣을 때 "어느 서버끼리 통신" 이 아니라 **"어느 쪽이 먼저 말을 거는가"** 를 정해야 한다. 응답 패킷은 상태 추적(stateful)이 알아서 돌려보내주므로, 요청 방향 한 줄만 열면 된다.

## 두 가지 기본 성질

**기본은 거부다.** 규칙에 없으면 막힌다(implicit deny). 그래서 "안 되는데요" 의 대부분은 장애가 아니라 **아직 열지 않은 것**이다. [[edge 방화벽 — VPN이 뚫어주지 않는 내부 접근]] 에서 VPN 을 붙였는데도 막혔던 게 정확히 이 성질이다 — 입장(VPN)은 허가됐지만 그 서비스로 가는 줄이 ACL 에 없었다.

**위에서부터 첫 일치에서 멈춘다.** 그래서 순서가 의미를 바꾼다. 넓은 거부 규칙이 좁은 허용 규칙보다 위에 있으면 아래 줄은 영원히 안 읽힌다. 규칙을 추가했는데 안 먹으면 대개 내용이 아니라 **위치** 문제다.

## 출발지 IP 는 고정되어야 한다

ACL 이 출발지로 사람을 식별하지 않고 **IP** 로 식별한다는 게 실무에서 제일 자주 걸리는 지점이다. 상대가 우리를 허용 목록에 넣으려면 우리 쪽 출발지 IP 가 변하지 않아야 한다.

[[Pod]] IP 처럼 재배포마다 바뀌는 주소를 적으면 등록이 곧 무용지물이 된다. 그래서 나가는 트래픽을 게이트웨이에서 고정 IP 하나로 바꿔치기하고(SNAT) **그 대표 IP 를 상대 ACL 에 올린다.** 자세한 흐름은 [[네트워크 경계 (ingress·egress·NAT)]] 의 egress NAT IP 절.

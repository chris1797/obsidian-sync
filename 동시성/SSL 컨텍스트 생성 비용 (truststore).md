# SSL 컨텍스트 생성 비용 (truststore)

[[FastAPI 요청당 CPU 줄이기]]에서 "클라이언트를 재사용하라" 는 처방을 적었는데, 그 처방이 **왜** 듣는지를 쪼개 보니 범인은 TCP 연결도 TLS 핸드셰이크 암호 연산도 아니었다. **인증서 저장소를 읽는 일**이었다.

## 무엇이 비싼가

`truststore` 는 파이썬 TLS 검증을 OS 인증서 저장소에 맡기는 라이브러리다. 그런데 Linux 에서는 `SSLContext` 를 하나 만들 때마다 `set_default_verify_paths` 로 **시스템 CA 묶음 전체를 다시 읽어 파싱**한다. 1회에 약 5ms.

비유하면 — 손님(연결)이 올 때마다 신분증 위조 여부를 보려고 **전국 도장 대장 전체를 도서관에서 새로 빌려 오는** 셈. 확인 자체(핸드셰이크)보다 대장 빌려 오는 데 시간이 더 든다.

이게 연결 단위 비용이 되는 경로:

```
호출마다 httpx 클라이언트 새로 생성
  → 클라이언트마다 SSLContext 새로 생성
    → 컨텍스트마다 CA 전체 재로딩 (~5ms CPU)
      → 요청 수만큼 곱해짐 → cProfile 1위
```

## 처방 — 컨텍스트만 하나로

```python
SSL_CTX = ssl.create_default_context()      # 프로세스에 하나
client = httpx.AsyncClient(verify=SSL_CTX)  # 매번 새 클라이언트여도 컨텍스트는 공유
```

- **연결 풀을 공유하지 않아도** CPU 대부분이 돌아온다 — 비용이 연결이 아니라 컨텍스트 생성에 있었으니까.
- 검증 강도는 그대로다. 같은 CA 로 같은 검증을 하고, 대장을 한 번만 빌려 둘 뿐.
- `SSL_CERT_FILE` 환경변수만 지정해도 줄긴 하지만(읽을 대상이 파일 하나로 고정) 컨텍스트 공유보다 덜 줄어든다. 여전히 매번 읽기는 하니까.

## 교훈 — 처방 전에 비용을 분리

"클라이언트 재사용" 은 연결·핸드셰이크·컨텍스트·세션을 한 덩어리로 묶은 처방이다. 덩어리째 처방하면 왜 듣는지 모르고, 덩어리를 통째로 못 바꿀 때(예: 라이브러리가 클라이언트를 내부에서 만든다) 손쓸 곳도 안 보인다. **프로파일로 진짜 비용을 하나씩 떼어 보면**, 덩어리 중 한 조각(여기선 CA 로딩)만 고쳐도 대부분이 해결되는 경우가 있다. 연결 재사용 쪽이 왜 기대만큼 안 듣는지는 [[Streamable HTTP 응답 형식과 연결 재사용]]에서 이어진다.

> 왜 여기 붙나: "요청마다 반복되는 셋업 비용" 의 한 조각 — 연결이 아니라 SSL 컨텍스트 생성(CA 로딩)이 진짜 비용이었다

# FastAPI 요청당 CPU 줄이기

CPU 가 높으면 먼저 "무거운 계산이 어디 있나" 를 찾게 된다. 그런데 실제로 본 경우는 계산이 아니었다 — **요청마다 반복되는 셋업 비용**이 [[FastAPI 동시성 모델]]의 이벤트 루프 하나에 몰린 것이었다. 요청 하나에 3~4초가 걸리는데 CPU 는 수백 m 인 앱이면, 시간의 대부분은 외부 응답 대기이고 CPU 는 그 앞뒤 준비 작업이 먹는다.

[[HTTP 헤더 오버헤드]]에서 본 "무상태의 청구서" 와 같은 구조다. 아무것도 기억하지 않으면 매 요청이 맥락을 처음부터 다시 만든다 — 그 노트에선 바이트로, 여기선 CPU 로 청구된다.

## 0. 계측이 먼저

추측으로 고치면 안 된다. 최소한:

- 지연 히스토그램 버킷이 실제 분포를 덮는가. 기본 버킷이 1초에서 끝나면 "72% 가 1초 초과" 까지만 보이고 그 위는 깜깜하다.
- **자기 시간 vs 외부 대기 시간을 분리.** 게이트웨이·프록시형 앱이면 특히 — 둘이 섞여 있으면 어디를 줄여야 할지 모른다.

## 1. 연결·세션 재사용 — 가장 큰 레버

외부 호출마다 클라이언트를 새로 만들면, 매번 TCP 연결 + TLS 핸드셰이크 + (프로토콜에 따라) 세션 initialize 를 다시 한다. TLS 는 CPU 를 먹는 암호 연산이고, 클라이언트·세션 객체 생성에도 직렬화·검증 비용이 붙는다.

- `httpx.AsyncClient` 를 앱 수명 동안 **하나** 두고 keep-alive 로 연결을 재사용
- 상위 프로토콜 세션(MCP 등)도 가능하면 프로필·대상별로 재사용
- 무상태(stateless) 모드를 쓰면 `initialize`·목록 조회 같은 준비 요청도 매번 전 과정을 다시 탄다 — 캐시할 수 있는 건 캐시

## 2. async 안의 동기 I/O 를 루프 밖으로

[[FastAPI 동시성 모델]]의 "가장 흔히 밟는 지뢰" 그대로다. `async def` 안에서 동기 DB 드라이버를 부르면 그동안 **워커 전체가 멈춘다.** 평소엔 요청당 수~수십 ms 라 안 보이다가, DB 가 느려지는 순간 read timeout 만큼 파드 전체가 정지한다. CPU 를 직접 먹는 문제라기보다 **처리량과 꼬리 지연**의 문제지만, 루프가 막히면 뒤에 쌓인 요청이 한꺼번에 몰려 CPU 스파이크로도 보인다.

- 근본: async 드라이버([[AsyncSession]])
- 당장: `await asyncio.to_thread(동기함수)` 로 빼기
- 로그·감사처럼 응답에 필요 없는 쓰기는 큐로 넘겨 요청 경로에서 제거

⚠️ `to_thread` 가 쓰는 기본 executor 크기는 `min(32, os.cpu_count() + 4)`. 그런데 컨테이너 안의 `os.cpu_count()` 는 CPU limits 가 아니라 **노드 전체 코어 수**를 본다. 노드 6코어면 10스레드 — 동시 요청이 많으면 여기서 줄을 선다. DB 커넥션 풀 크기와 맞춰 `loop.set_default_executor()` 로 명시하는 게 낫다.

## 3. 매 요청 DB 왕복을 캐시·디바운스

"요청마다 세션 확인 + last_used_at 갱신" 같은 코드는 호출 빈도가 가장 높은 경로에 붙어 있어서 비용이 곱해진다.

- 확인 결과는 짧은 TTL(수 초~수십 초) 캐시
- `touch` 류 갱신은 디바운스 — 마지막 갱신 후 60초 안이면 생략

정확도를 조금 내주고 왕복 횟수를 크게 줄이는 거래다.

## 4. 직렬화 비용

큰 JSON 을 파싱했다가 필드 하나 넣고 다시 덤프, 큰 스키마 목록을 pydantic 으로 매번 직렬화 — 하나하나는 작아도 요청 수만큼 곱해진다. 변하지 않는 응답은 직렬화된 바이트째 캐시하고, 파싱·재직렬화 왕복은 필요한 경우로만 줄인다. 필요하면 `orjson` 같은 빠른 직렬화기.

## 5. 워커 수를 늘리기 전에

[[GIL]] 때문에 워커 1개 = 사실상 코어 1개가 상한. 그래서 `--workers N` 이 정석 같지만 함정이 있다.

- **메모리 상태가 워커마다 갈라진다.** 인메모리 rate limit·동시성 카운터·캐시가 워커별로 따로 생겨, 사용자당 제한이 사실상 N배로 느슨해진다. 캐시 적중률도 1/N.
- 메모리도 워커 수만큼 늘어 메모리 limits(OOM)에 가까워진다.

컨테이너 환경이면 워커를 늘리기보다 **파드 수로 확장**([[HPA]])하는 편이 상태 문제를 드러내기 쉽다. 어느 쪽이든 공유 상태는 Redis 같은 외부로 빼야 진짜로 풀린다. 그리고 1~4번으로 요청당 비용을 먼저 깎는 게, 같은 트래픽을 적은 CPU 로 처리하게 만드는 유일한 방법이다 — 스케일링은 비용을 나눌 뿐 줄이지 않는다.
